AI 에이전트를 개발하려면 무엇부터 만들어야 할까요? LLM API를 호출하는 코드, 도구 목록, 도구 선택용 라우터, 여러 단계를 실행하는 루프, 작업 기록, 오류 복구, 그리고 사용자가 결과를 볼 웹 화면을 떠올릴 수 있습니다.

그런데 이 목록의 상당 부분은 이미 다른 사람들이 만든 에이전트 프레임워크와 하네스가 제공하는 기능입니다. 모델이 직접 코드를 작성해 계산하고, 파일을 만들고, 도구 실행에 실패하면 다른 방법을 시도하는 환경도 있습니다. 같은 일을 위해 전용 실행 엔진을 다시 만들어야 하는지 묻게 됩니다.

이 질문에 답하려면 두 가지를 구분해야 합니다. **업무에 특화된 AI 에이전트를 만드는 일**과 **에이전트를 움직이는 실행 하네스를 직접 만드는 일**은 같지 않습니다.

이 글은 2026년 10월 기준의 공개 자료를 토대로, 무엇이 실제로 달라졌는지와 어디까지 일반화할 수 있는지를 살펴봅니다. 여기서 다루는 것은 기술·아키텍처의 변화이며, 모든 기업의 개발 방식이 이미 전환됐다는 주장은 아닙니다.

## 전용 에이전트와 전용 하네스는 다른 문제입니다

에이전트 하네스(Agent Harness)는 모델이 작업을 수행할 수 있도록 주변에서 실행을 조정하는 프로그램입니다. 모델 요청에 어떤 맥락을 넣을지, 어떤 도구를 제시할지, 도구 호출을 허용할지, 결과를 어디에 저장할지, 실패하면 어떻게 복구할지 등을 관리합니다.

반면 전용 에이전트는 특정 업무 문제를 해결하는 시스템입니다. 고객지원 에이전트라면 고객 데이터와 상담 정책을 이해해야 하고, 데이터 분석 에이전트라면 통계의 의미와 검증 기준을 알아야 합니다. 이러한 업무 지식은 직접 만든 하네스 위에 있을 수도 있고, 기존 하네스 위에 있을 수도 있습니다.

| 구분 | 주된 관심사 | 재사용 가능한 부분 |
| --- | --- | --- |
| LLM | 주어진 맥락에서 추론하고 응답·도구 요청을 생성 | 모델 API |
| Agent Harness | 도구 실행, 반복 루프, 문맥, 상태, 권한, 복구 | SDK, 오픈소스 런타임, 관리형 서비스 |
| 전용 Agent | 특정 업무의 목표·데이터·정책·판정 기준 | 범용 하네스 위에서 특화 가능 |
| 사용자 애플리케이션 | 대시보드, 승인 화면, 차트, 다운로드, 업무 흐름 | 기존 웹앱·컴포넌트·API |

하네스의 기본 개념이 낯설다면 이 블로그의 [AI 에이전트와 하네스: 처음부터 설명하기](/blog/ai-agent-harness)를 먼저 읽어도 좋습니다. 여기서는 구현 원리보다 개발 전략에 집중하겠습니다.

## 2026년에는 무엇이 달라졌을까요?

### 실행 하네스가 독립적인 제품과 서비스가 되고 있습니다

[OpenAI의 Codex Harness 설명](https://openai.com/index/unlocking-the-codex-harness/)은 하나의 공통 실행 하네스를 CLI, IDE, 앱 등 여러 인터페이스가 공유하는 구조를 보여줍니다. 개발자가 제품 화면마다 다른 실행 루프를 만들 필요가 없도록 런타임과 클라이언트를 분리한 사례입니다.

[Anthropic의 Managed Agents 설명](https://www.anthropic.com/engineering/managed-agents)은 세션, 하네스, 샌드박스를 서비스 차원에서 관리하는 접근을 제시합니다. [AWS의 Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)도 Runtime, Gateway, Memory, Identity, Observability 같은 운영 요소를 분리해 제공합니다. OpenAI 역시 [Agent 개발 방식](https://developers.openai.com/api/docs/guides/agents)에서 관리형 실행 환경, Agents SDK, 직접 모델 API 호출을 서로 다른 선택지로 안내합니다.

이 사례들이 보여주는 **확인된 사실**은 공급 측면의 변화입니다. 실행 루프와 도구·상태·보안 인프라를 직접 만들지 않고 확보할 수 있는 선택지가 늘어났습니다.

하지만 이것만으로 기업의 자체 하네스 개발이 몇 퍼센트 감소했는지는 알 수 없습니다. 공급자가 제품을 출시했다는 사실과 시장 전체가 그 제품으로 이동했다는 사실은 다릅니다.

### 기존 도구는 버리는 대신 연결할 수 있습니다

도구 재사용의 대표적인 연결 방식은 MCP(Model Context Protocol)입니다. 기존 계산 함수, 사내 API, 검색 시스템을 MCP 도구로 노출하면 이를 지원하는 하네스가 해당 도구를 호출할 수 있습니다.

여기서 중요한 차이가 있습니다. **도구를 호출할 수 있다는 것과 도구를 정확하게 선택하고 올바르게 사용한다는 것은 별개**입니다. 입력값, 도구 권한, 오류 처리, 계산 결과의 검증은 여전히 필요합니다.

또 하나의 변화는 UI입니다. [MCP Apps](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)는 지원하는 호스트 안에서 외부 도구가 그래프, 테이블, 입력 폼 같은 인터랙티브 화면을 제공할 수 있도록 합니다. [AG-UI](https://github.com/ag-ui-protocol/ag-ui)는 기존 웹 프런트엔드와 에이전트 실행 환경 사이에서 메시지·상태·이벤트를 전달하는 인터페이스를 제공합니다.

세 가지를 구분하면 다음과 같습니다.

- **MCP Tool:** 에이전트가 업무 도구를 호출할 수 있게 연결합니다.
- **MCP Apps:** 지원하는 대화형 호스트 안에 업무용 웹 UI를 표시할 수 있습니다.
- **AG-UI:** 별도의 웹앱과 에이전트 백엔드가 실행 상태를 주고받도록 연결합니다.

따라서 계산기나 시각화 코드를 새로 만드는 것보다, **이미 검증된 도구와 기존 UI를 어느 환경에 어떻게 연결할지**가 더 중요한 개발 문제가 될 수 있습니다. 단, MCP를 지원하는 모든 클라이언트가 MCP Apps도 지원하는 것은 아니고, 기존 React·Vue·서버 중심 웹앱의 이식 난이도도 다릅니다.

### 반복 실행보다 검증과 운영이 더 큰 문제로 부상합니다

모델을 여러 번 호출하는 반복문은 에이전트의 출발점일 뿐입니다. 장시간 실행 중단, 문맥 한도, 권한 확인, 외부 시스템 변경, 실패 복구와 같은 문제를 해결해야 운영할 수 있습니다.

[LangGraph의 상태 지속성 문서](https://langchain-ai.github.io/langgraphjs/concepts/persistence/)는 체크포인트와 작업 재개가 왜 필요한지 보여줍니다. [Anthropic의 Agent 평가 가이드](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)는 모델의 최종 답변뿐 아니라 실제 실행 결과와 도구 사용 경로를 평가해야 한다고 설명합니다.

이것은 **완료했다는 응답**과 **외부 시스템에서 목표가 실제 달성된 상태**를 구분해야 한다는 뜻입니다.

## 그렇다면 기업들은 전용 에이전트를 덜 만들고 있을까요?

이 질문에는 아직 신중하게 답해야 합니다.

2026년 6월 공개된 [LangChain의 State of Agent Engineering 조사](https://www.langchain.com/state-of-agent-engineering)에서 응답자 57.3%는 에이전트를 운영 환경에서 사용한다고 답했습니다. 약 89%는 어떤 형태로든 관측 기능을 사용했고, 52.4%는 오프라인 평가를 수행한다고 응답했습니다.

다만 조사 기간은 **2025년 11~12월**이고, 응답자는 1,340명이며 그중 기술 업종 비중이 63%입니다. 따라서 이 수치를 모든 기업의 보급률로 바꾸어 쓰면 안 됩니다. 더구나 이 조사는 자체 개발 하네스와 재사용 하네스의 시장 점유율 변화를 직접 측정한 자료가 아닙니다.

반대 방향의 변화도 존재합니다. [McKinsey의 2026년 AI 조사](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai)에서는 에이전트 활용이 확대되는 동시에, Agentic Coding으로 기존 소프트웨어를 구매하는 대신 내부에서 직접 기능을 만드는 사례도 보고됩니다. 여기서 **내부 소프트웨어 개발 증가**와 **Agent Harness 직접 개발 증가**는 서로 다른 현상입니다.

범용 하네스가 성숙할수록 전용 애플리케이션을 만드는 일이 줄어들 수도 있지만, 반대로 그 비용을 낮추어 더 많은 전용 애플리케이션이 등장할 수도 있습니다. 두 효과 중 어느 쪽이 더 큰지는 현재 공개된 자료만으로 확정하기 어렵습니다.

## 다시 만들 필요가 없는 것과 직접 소유해야 하는 것

기존 하네스가 파일을 읽고, Python을 실행하고, 검색 도구를 호출하며, 표나 그래프를 생성할 수 있다면 그 기능을 처음부터 다시 구현할 이유는 약해집니다.

그러나 도구의 실행 능력과 업무적 정확성은 다릅니다. 예를 들어 판매 보고서를 만든다고 가정해 보겠습니다. 에이전트가 SQL을 작성하고 월별 매출을 집계하는 일은 기존 하네스에 맡길 수 있습니다. 하지만 주문 취소를 매출에서 어떻게 차감할지, 세금을 포함할지, 환율 적용 시점은 언제인지 같은 정의는 조직이 결정해야 합니다.

다른 업무에서도 역할 분담은 비슷합니다.

| 기존 하네스에 맡기기 좋은 영역 | 자체적으로 보유할 이유가 큰 영역 |
| --- | --- |
| 일반 도구 호출·반복 루프·재시도 | 업무 데이터의 의미와 품질 |
| 일회성 코드 실행·탐색적 분석 | 검증된 공식 계산식과 정합성 규칙 |
| 유연한 차트·문서 초안 생성 | 반복 사용하는 대시보드·사용자 경험 |
| 공통 세션·문맥 관리 | 업무별 승인·권한·감사 기준 |
| 범용 추론 및 작업 분해 | 실제 성공 여부를 판단하는 테스트·평가 |

특히 돈의 이동이나 중요 데이터 변경처럼 되돌리기 어려운 작업은 모델의 자연어 판단에만 맡겨서는 안 됩니다. 실행 도구가 권한·승인·조건을 독립적으로 확인하도록 설계해야 합니다. [OWASP의 Agentic Applications 보안 자료](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)도 이런 종류의 위험을 다룹니다.

**범용 하네스를 재사용한다는 것은 업무 책임까지 외부에 맡긴다는 뜻이 아닙니다.**

## Build, Buy, Blend, 그리고 아무것도 만들지 않는 선택

전용 에이전트 개발을 검토할 때는 처음부터 자체 하네스와 관리형 서비스 둘 중 하나를 선택할 필요가 없습니다. 가능한 선택지는 여러 단계로 나뉩니다.

| 선택 | 적합한 상황 | 주의할 점 |
| --- | --- | --- |
| 기존 시스템 유지 | 정해진 규칙·SQL·BI·일반 코드로 충분한 경우 | 에이전트 도입 자체가 추가 복잡성이 될 수 있음 |
| LLM API 직접 호출 | 요약·분류·추출처럼 짧은 처리 | 다단계 실행과 복구가 필요하면 부족할 수 있음 |
| Agent SDK | 기존 애플리케이션 안에 실행 루프를 넣고 싶을 때 | SDK 버전·모델 의존성을 관리해야 함 |
| 관리형 Harness | 장시간 실행·샌드박스·상태 관리 운영을 줄이고 싶을 때 | 비용·데이터 처리 위치·확장 제약 확인 |
| 기존 앱과 Harness 결합 | 이미 데이터·도구·웹 UI 자산을 보유한 경우 | 인증·UI 호환성·상태 연결 비용이 발생 |
| 자체 Harness | 특별한 실행 환경이나 강한 통제가 차별화의 핵심인 경우 | 공통 인프라를 직접 유지해야 함 |

[Gartner의 2026년 Build / Buy / Blend 관련 연구](https://www.gartner.com/en/documents/8108997)는 이러한 의사결정 자체가 별도의 경영·기술 문제로 다뤄지고 있음을 보여줍니다. 여기서 표의 세부 기준은 공개 자료를 바탕으로 구성한 분석적 틀이며, 유료 보고서의 미열람 내용을 대신 옮긴 것은 아닙니다.

먼저 **이 업무에 에이전트가 정말 필요한가**를 확인하는 편이 합리적입니다. [Anthropic의 Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)도 간단한 방법으로 해결할 수 있을 때 불필요하게 에이전트 구조를 늘리지 않는 접근을 강조합니다.

## 도입의 성패는 무엇으로 평가해야 할까요?

기존 하네스가 답변을 더 길고 그럴듯하게 만든다는 이유만으로 우수하다고 판단하기는 어렵습니다. 같은 작업과 같은 데이터, 유사한 실행 예산을 주고 비교해야 합니다.

검증할 핵심 지표는 다음과 같습니다.

1. **검증된 작업 완료율:** 실제 파일, 데이터베이스, 업무 상태가 성공 조건을 충족했는가.
2. **완료 한 건당 총비용:** 토큰·도구·인프라뿐 아니라 사람의 검토와 복구 비용을 포함했는가.
3. **안전성:** 승인 우회, 금지된 데이터 접근, 예상하지 못한 외부 변경이 발생하지 않았는가.
4. **재현성과 추적성:** 같은 작업을 반복할 때 일관된 결과를 얻고 실패 경로를 추적할 수 있는가.
5. **통합과 유지보수 부담:** SDK 업그레이드, 호환성, 플랫폼 변경을 감당할 수 있는가.

예컨대 모델 API 비용이 싸더라도 같은 일을 여러 번 실패하고 사람이 수정한다면 완료 한 건의 비용은 비쌀 수 있습니다. 반대로 관리형 하네스의 호출 비용이 높아도 복구와 운영에 쓰는 시간이 크게 줄면 전체 비용은 낮아질 수 있습니다.

어느 방식이 보편적으로 몇 퍼센트 효율적이라는 수치는 **알 수 없음**입니다. 실제 업무를 대표하는 평가 세트와 비용 기록이 필요합니다.

## 자체 하네스 개발이 여전히 합리적인 경우

기존 하네스 재사용이 항상 답은 아닙니다. 폐쇄망이나 특수 하드웨어, 실시간 제어, 강한 데이터 주권 요건이 있다면 지원되는 실행 환경 자체가 제한적일 수 있습니다.

또한 에이전트의 스케줄링, 문맥 관리, 복구 알고리즘이 제품의 핵심 연구 주제라면 그것을 직접 개발하는 일이 곧 차별화일 수 있습니다. 장기간 대량 실행하는 서비스에서 자체 운영의 비용 우위가 실측되는 경우도 예외입니다.

여기서 중요한 것은 선택의 이유입니다. **일반적인 도구 라우터를 만들 수 있다는 사실**과 **그 라우터를 직접 소유해야 할 경제적·기술적 이유가 있다는 사실**은 다릅니다.

## 이 판단을 언제 다시 검토해야 할까요?

이 글의 판단은 2026년 10월 9일 현재의 기술·제품 문서와 앞서 언급한 조사의 공개 내용에 한정됩니다. 다음과 같은 결과가 나오면 재사용 우위라는 해석을 축소해야 합니다.

- 동일 작업 평가에서 기성 하네스의 정확성·복구·보안 성능이 지속적으로 떨어지는 경우
- 기존 UI와 도구를 연결하는 비용이 자체 실행 환경을 유지하는 비용보다 커지는 경우
- 공급자의 데이터 처리 정책이나 가격이 업무 요구에 맞지 않게 바뀌는 경우
- 특정 업무에서 자체 설계한 실행 방식의 검증 가능한 품질 우위가 나타나는 경우

반대로 자체 하네스의 개발·유지 비용이 계속 증가하고 같은 목표를 기성 하네스로 더 안정적으로 달성한다면 직접 구현을 유지할 근거는 약해집니다.

기술 변화가 빠르므로 이 판단은 **2027년 1~4월에 재검토**하는 것이 적절합니다. 그 전에 주요 플랫폼의 기능·정책·가격에 중대한 변화가 발생한다면 더 일찍 확인해야 합니다.

## 마지막 판단

현재 확인되는 변화는 **전용 AI 에이전트의 소멸**이 아니라 **전용 에이전트를 만들기 위해 실행 하네스까지 매번 직접 개발해야 할 필요성이 줄어드는 것**입니다.

앞으로 많은 업무에서는 모델을 반복 호출하는 기반보다, 모델이 접근할 수 있는 데이터의 의미, 이미 검증된 업무 도구, 사용자에게 전달할 인터페이스, 실제 결과를 검증하는 방법이 더 중요한 개발 자산이 될 수 있습니다.

그렇다고 모든 조직이 관리형 에이전트로 이동한다거나 자체 하네스가 불필요해질 것이라고 단정할 근거는 없습니다. 산업 전체의 개발 방식별 점유율 변화는 아직 충분히 확인되지 않았습니다.

따라서 새로운 에이전트를 구상할 때 질문의 순서를 바꿔볼 필요가 있습니다. **“무슨 에이전트를 직접 만들까?”보다 “기존 실행 환경으로 해결할 수 없는 문제가 정확히 무엇인가?”를 먼저 묻는 것**입니다. 그 차이를 실제 품질·위험·비용으로 입증할 수 있을 때 비로소 자체 하네스 개발은 정당화됩니다.
