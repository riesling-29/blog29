한 조직이 사내 데이터 분석 에이전트를 개발한다고 가정해 봅니다. 사용자가 "지난 분기 주문 지연이 늘어난 이유를 그래프로 분석해 줘"라고 질문하면, 에이전트는 데이터베이스를 조회하고, 수치를 계산하고, 이상 구간을 찾고, 그래프를 만들고, 결과를 파일로 내보내야 합니다.

이런 시스템을 직접 만들기 시작하면 금방 해야 할 일이 늘어납니다. LLM에 어떤 도구를 알려줄지, 모델이 호출한 도구를 어떻게 실행할지, 실패하면 언제 재시도할지, 지난 대화와 작업 상태를 어디에 보관할지, 파일 다운로드 버튼을 어떻게 붙일지까지 설계해야 합니다.

그런데 상당수 기능은 이미 공개된 에이전트 하네스(Agent Harness)와 실행 플랫폼에 있습니다. **업무 전용 AI를 만든다는 이유만으로 범용 실행 엔진까지 직접 만들어야 할까요?**

이 질문을 검토하려면 '전용 에이전트'와 '전용 하네스'를 나누어 생각해야 합니다. 2026년 10월 현재 확인되는 변화는 후자의 재사용 선택지가 빠르게 구체화되고 있다는 것입니다. 그렇다고 전용 에이전트 개발 자체가 감소했다고 말할 통계가 충분한 것은 아닙니다.

## 에이전트가 하는 일과 하네스가 하는 일

LLM은 전달받은 정보에 따라 텍스트나 도구 호출 요청을 만듭니다. 도구 호출이 출력됐다고 해서 파일이 실제로 수정되거나 계산이 끝난 것은 아닙니다. 그 요청을 받아 입력값을 검사하고, 권한을 확인하고, 도구를 실행한 뒤 결과를 모델에 다시 전달하는 프로그램이 필요합니다. 이것이 하네스의 핵심 역할입니다.

모델의 판단, 하네스의 통제, 실행 환경의 작업은 하나로 보이지만 책임은 다릅니다. 예를 들어 모델이 `run_tests` 도구를 선택하면 하네스가 요청을 처리하고, 별도의 실행 환경에서 테스트가 돌아갑니다. 실패 메시지가 돌아오면 모델이 다음 수정을 제안할 수 있지만, 실제 파일 변경은 승인된 도구가 수행합니다.

여기서 **업무 전용 에이전트**는 한 단계 다른 개념입니다. 고객지원 에이전트라면 환불 조건과 고객 정보 접근 정책을 알아야 하고, 재무 분석 에이전트라면 집계 기준과 회계 기간을 정확하게 다뤄야 합니다. 이 지식과 검증 기준은 자체 하네스 위에도, 재사용한 하네스 위에도 올릴 수 있습니다.

| 구분 | 책임의 중심 | 다른 시스템으로부터 재사용할 수 있는 것 |
| --- | --- | --- |
| LLM | 요청 해석, 다음 행동 제안, 결과 설명 | 모델 API |
| Agent Harness | 실행 반복, 도구 연결, 문맥·세션 관리, 권한·오류 처리 | SDK, 오픈소스 런타임, 관리형 서비스 |
| 업무 전용 Agent | 업무 목표, 데이터 의미, 성공 조건, 고유 정책 | 하네스를 재사용하더라도 직접 정의할 부분 |
| 웹앱·UI | 차트, 데이터 테이블, 승인, 다운로드, 사용자 경험 | 기존 화면·컴포넌트·서비스 API |

기본 개념부터 보고 싶다면 앞서 작성한 [AI 에이전트와 하네스: 처음부터 설명하기](/blog/ai-agent-harness)에서 도구 호출과 실행 루프의 관계를 살펴볼 수 있습니다.

## 1. 같은 실행 엔진을 여러 제품 화면에서 사용한다

코딩 에이전트를 터미널에서 사용하다가 IDE에서도 제공하려면 어떤 문제가 생길까요? 터미널 화면과 IDE 화면은 다르지만 코드 검색, 파일 수정, 테스트 실행, 작업 중단과 재개의 규칙까지 두 벌로 만들 이유는 없습니다.

Codex는 이 문제를 **공통 하네스와 화면을 분리하는 구조**로 풀었습니다. 웹, CLI, IDE 확장, 데스크톱 앱이 공통 Codex 실행 엔진을 사용하고, 그 사이에 App Server가 놓입니다. App Server는 양방향 JSON-RPC 통신으로 사용자 요청을 실행 엔진에 전달하고, 진행 상황과 결과를 다시 클라이언트에 보냅니다. 새 화면을 만들 때 전체 에이전트 루프를 다시 구현하기보다, 실행 엔진에 연결되는 클라이언트를 개발하는 방식입니다.

여기에는 단순한 질문·답변을 넘어서는 상호작용이 포함됩니다. 한 번의 코드 수정 요청으로 파일 읽기, 패치 생성, 테스트, 재수정이 이어질 수 있고, 클라이언트는 중간 단계와 코드 차이(diff)를 받아 보여줍니다. 파일 변경에 승인이 필요하면 서버가 클라이언트에 승인 요청을 보내고, 사용자의 응답을 받은 후 실행을 계속할 수 있습니다. 작업 상태가 서버에 남으므로 클라이언트 창이 사라졌다고 해서 모든 진행 상태를 화면 쪽에서 다시 만들어야 하는 것도 아닙니다.

이것은 '하네스 = 사용자 채팅 화면'이라는 결합을 풀어낸 사례입니다. **같은 실행 기능 위에 코드 리뷰 화면, 운영 대시보드, 다른 업무용 UI를 붙일 수 있다는 설계상의 이점**이 생깁니다. 다만 Codex의 App Server가 모든 유형의 비즈니스 Agent를 즉시 지원한다는 뜻은 아닙니다. 실제 사례는 코딩 하네스와 그 클라이언트 구조에 관한 것입니다. ([OpenAI, *Unlocking the Codex harness*, 2026-02-04](https://openai.com/index/unlocking-the-codex-harness/))

## 2. 장시간 실행은 모델의 문제가 아니라 운영 구조의 문제이기도 하다

에이전트가 몇 분 이상 작업한다고 가정해 봅시다. 실행 중 코드를 돌리는 컨테이너가 중단되거나, 하네스 프로세스가 재시작되거나, 모델의 문맥 길이가 한계에 가까워질 수 있습니다. 이때 '재시도하세요'라고 프롬프트에 적는 것만으로 복구가 보장되지는 않습니다.

Anthropic의 관리형 에이전트 설계는 **세션 기록(session), 실행 하네스(harness), 코드 실행 공간(sandbox)을 분리**합니다. 처음에는 세 구성 요소를 한 컨테이너에 넣었지만, 컨테이너 장애가 세션 손실과 디버깅의 어려움으로 이어졌습니다. 이를 해결하기 위해 세션 이벤트를 실행 프로세스 밖에 지속적으로 저장하고, 하네스나 샌드박스를 교체해도 기록을 읽어 작업을 재개하도록 만들었습니다.

실제 인터페이스도 구체적입니다. 샌드박스는 하네스에서 `execute(name, input)` 같은 도구 인터페이스로 호출하고, 하네스가 중단되면 새 프로세스가 저장된 세션을 읽어 이어갈 수 있도록 `wake(sessionId)`, `getSession(id)`, `emitEvent(id, event)` 같은 경계를 둡니다. 중요한 것은 함수 이름 자체가 아니라 **세션 기록이 개별 실행 프로세스의 생존에 묶이지 않는다는 점**입니다.

이 분리는 보안에도 영향을 줍니다. 모델이 생성한 코드를 실행하는 샌드박스에 외부 시스템 자격증명을 그대로 넣으면, 악성 코드나 프롬프트 인젝션으로 그 자격증명을 노출할 위험이 있습니다. 관리형 설계에서는 토큰을 샌드박스 밖의 저장소에 두고, 필요한 도구 요청은 프록시를 거쳐 실행하도록 합니다. 실행 공간과 비밀정보를 구조적으로 분리하는 것입니다.

Anthropic은 이 아키텍처 전환 이후 자기 서비스의 첫 토큰 도착 시간이 중앙값 기준 약 60%, 95백분위 기준 90% 넘게 줄었다고 보고합니다. **특정 회사의 기존·변경 아키텍처를 비교한 결과**이지, 모든 관리형 에이전트가 그만큼 빨라진다는 범용 벤치마크는 아닙니다. ([Anthropic, *Scaling Managed Agents: Decoupling the brain from the hands*, 2026-04-08](https://www.anthropic.com/engineering/managed-agents))

이 사례가 시사하는 것은 분명합니다. Agent를 계속 실행시키는 품질은 모델 성능뿐 아니라 이벤트 기록, 장애 복구, 자격증명, 격리된 실행 환경을 어떻게 배치하는지에도 좌우됩니다. 범용 플랫폼을 활용하면 이 인프라를 처음부터 설계할 부담을 줄일 수 있습니다.

## 3. 도구와 UI도 실행 엔진에서 분리되고 있다

### 기존 계산기와 조회 API는 그대로 활용할 수 있다

업무별 계산기나 검색기를 이미 갖고 있다면 그것을 버릴 필요는 없습니다. 예를 들어 `get_orders`, `calculate_lead_time`, `export_csv` 같은 기존 함수나 API를 일관된 입력·출력 계약으로 노출할 수 있습니다. 그러면 하네스는 사용자의 질문을 처리하다가 필요한 도구를 호출하고, 계산 자체는 기존 검증된 코드가 맡습니다.

여기에 MCP(Model Context Protocol)가 연결 지점을 제공합니다. 핵심은 에이전트가 외부 도구의 이름, 설명, 입력 형식을 공통 방식으로 발견하고 호출할 수 있다는 점입니다. AWS의 AgentCore Gateway처럼 기존 API나 서버리스 함수를 MCP 도구로 변환해 에이전트에 제공하는 서비스도 등장했습니다. 별도의 AgentCore Harness는 모델, 시스템 프롬프트, 도구를 지정해 관리형 실행을 맡기고, Memory·Identity·Observability 등의 기능을 선택적으로 결합할 수 있도록 구성돼 있습니다. **도구, 실행, 메모리, 권한을 한 덩어리로 직접 개발하지 않아도 되는 선택지가 있다는 것**입니다. ([AWS, *Amazon Bedrock AgentCore Overview*](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html))

다만 MCP로 도구가 보인다는 것은 그 도구를 올바르게 사용한다는 뜻이 아닙니다. 모델이 조회해야 할 기간을 잘못 선택하거나, 서로 다른 단위의 데이터를 더하면 계산 도구 자체가 정확하더라도 결과는 잘못될 수 있습니다. 따라서 업무 지표의 의미, 입력 검증, 읽기·쓰기 권한, 부작용 처리는 별도로 정의해야 합니다.

### 그래프와 다운로드 화면까지 연결하는 방법

도구 실행 결과가 텍스트 한 문단으로만 돌아온다면 별도의 웹앱을 만들고 싶어집니다. 그런데 분석 결과가 선 그래프, 필터 가능한 테이블, 승인 버튼으로 표시돼야 한다고 해서 반드시 별도의 에이전트 백엔드까지 필요할까요?

MCP Apps는 이 문제를 **도구 실행 결과와 대화창 안의 웹 UI를 연결**하는 방식으로 다룹니다. 도구는 자신과 연결될 HTML UI 리소스를 `ui://` 주소로 선언할 수 있고, 지원하는 호스트는 그 리소스를 가져와 격리된 iframe에 표시합니다. 차트의 화면 틀과 실제 데이터는 별도로 전달될 수 있으며, 사용자가 화면에서 새로고침이나 필터 조작을 하면 UI가 다시 도구 호출을 요청할 수도 있습니다. UI 코드가 모델의 답변 텍스트 자체에 들어갈 필요는 없습니다.

보안 경계도 명세에 포함됩니다. 호스트와 UI는 격리된 환경에서 통신하고, 허용된 도메인과 콘텐츠 보안 정책(CSP)을 적용합니다. 호스트는 어떤 기능을 지원하는지 협상해야 하므로, **MCP 도구 호출을 지원하는 클라이언트라도 MCP Apps UI를 표시하지 못할 수 있습니다.** 지원하지 않는 환경에서는 일반 텍스트 결과로 대체하는 설계가 필요합니다. ([MCP, *MCP Apps 공식 확장 발표*](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/), [MCP Apps 2026-01-26 사양](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx))

반대로 기존 회사 웹앱을 유지하고 Agent만 내부에 넣으려는 경우에는 다른 연결이 필요합니다. AG-UI는 에이전트 백엔드가 메시지, 도구 실행 진행, 상태 변경 등을 이벤트로 전달하고 프런트엔드가 이를 표시하도록 하는 프로토콜입니다. 예를 들어 사용자가 기존 대시보드의 조건을 바꾸면 Agent가 그 상태를 참고해 분석을 갱신하고, 다시 UI에 진행 상태와 결과를 돌려줄 수 있습니다. 즉 MCP Apps는 **호스트 대화창 안에 업무 UI를 넣는 방향**, AG-UI는 **기존 업무 UI에 Agent를 연결하는 방향**에 가깝습니다. 이 구분은 사용 경험을 설명하기 위한 것이며, 실제 구현에서는 두 기술을 결합할 수도 있습니다. ([AG-UI 공식 저장소 및 기능 개요](https://github.com/ag-ui-protocol/ag-ui))

아래는 새로운 제품을 발명한 예시가 아니라, 이런 연결을 이용해 구성할 수 있는 **가상의 운영 분석 서비스**입니다.

```text
사용자: "지역별 배송 지연 추이를 보여주고 CSV로 내려줘"
       |
       v
기존 Agent Harness — 질문 해석, 도구 선택, 실행 상태 관리
       |
       +--> 기존 API: 배송 이벤트 조회
       +--> 검증된 도구: 지연 시간 집계
       +--> UI: 지역별 선 그래프·필터 (MCP Apps 또는 기존 웹앱)
       +--> 기존 API: CSV 생성·다운로드
```

여기서 추가 개발은 완전히 0이 아닙니다. 입력 스키마, UI 호스트 호환성, 인증, 다운로드 URL, 실패 처리 같은 **통합 코드**가 필요합니다. 하지만 이미 존재하는 계산기·그래프·Export 기능을 다시 구현하는 일과는 작업 범위가 다릅니다.

## 4. 시장 조사에서는 무엇이 확인됐을까?

기술 공급자가 새로운 하네스를 내놓는다고 해서 시장 전체의 자체 개발이 감소했다고 단정할 수는 없습니다. 그 차이를 확인하기 위해 실제 조사 수치를 살펴볼 필요가 있습니다.

2026년 6월 발표된 LangChain 조사에서는 응답자 **57.3%가 에이전트를 운영 환경에서 사용 중**이라고 답했고, **30.4%는 운영 배포 계획을 갖고 개발 중**이라고 응답했습니다. 주요 사용 목적은 고객지원 **26.5%**, 조사·데이터 분석 **24.4%**, 내부 업무 자동화 약 **18%**였습니다. 사람들이 전용 업무 에이전트를 여전히 만들고 있다는 근거로 읽을 수 있습니다.

하지만 개발의 어려움은 단지 에이전트를 실행하는 데 있지 않았습니다. 응답자의 약 **32%는 품질을 운영 배포의 주요 장애 요인**으로 꼽았고, **20%는 지연 시간**을 주요 장애 요인으로 꼽았습니다. 실행 과정을 들여다보는 관측성(Observability)은 **89%**가 도입했다고 답한 반면, 사전에 정해진 문제로 품질을 시험하는 오프라인 평가(Offline Evals)는 **52.4%**, 실제 운영 과정에서 평가하는 온라인 평가는 **37.3%**에 그쳤습니다. *실행을 볼 수 있는 것*과 *실행 결과가 올바른지 검증하는 것* 사이에 간격이 있다는 뜻입니다.

조사는 **2025년 11월 18일~12월 2일, 1,340명**의 답변을 수집해 발표했습니다. 응답자의 **63%가 기술 업종**에 속했고, 공개 온라인 조사이므로 모든 기업의 상태를 대표하는 확률표본이라고 볼 수는 없습니다. 무엇보다 이 조사에는 **직접 제작 하네스의 시장 점유율이 몇 년간 어떻게 달라졌는지**를 보여주는 값이 없습니다. ([LangChain, *State of Agent Engineering*, 2026-06-12](https://www.langchain.com/state-of-agent-engineering))

전용 소프트웨어가 줄어든다고만 말하기 어려운 반대 증거도 있습니다. McKinsey의 2026년 8월 조사에서는 연매출 10억 달러를 넘는 대기업 응답자 중 **40%가 AI Agent를 확장 적용**한다고 답했습니다. 전년 조사에서 보고된 **27%**보다 높은 수치입니다. 그리고 전체 응답자 약 **32%는 Agentic Coding 도구를 활용해 내부에서 만들 수 있다는 이유로 소프트웨어 제품이나 기능의 구매를 한 번 이상 보류**했다고 답했습니다.

여기서 '내부 소프트웨어를 더 만든다'는 것은 'Agent Harness를 직접 더 만든다'는 말이 아닙니다. 범용 코딩 도구가 좋아질수록 **특화된 애플리케이션을 직접 만드는 일은 오히려 쉬워질 수 있습니다.** 따라서 '전용 에이전트의 소멸'과 '실행 인프라의 재사용'은 서로 다른 현상으로 보아야 합니다. ([McKinsey, *The State of AI in 2026: On the Road to ROI*, 2026-08-25](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-state-of-ai))

## 5. 하네스를 재사용해도 검증 기준은 직접 가져야 한다

에이전트가 "환불을 처리했습니다"라고 대답했다면 실제로 환불이 끝난 것일까요? 시스템에 환불 기록이 생성됐는지, 금액과 대상이 맞는지, 고객에게 승인된 알림이 나갔는지 확인해야 합니다. 답변이 설득력 있다는 사실과 업무 상태가 올바르다는 사실은 다릅니다.

에이전트 평가에서는 **작업(Task), 시도(Trial), 평가 로직(Grader), 실행 기록(Trace), 최종 상태(Outcome)**를 분리할 필요가 있습니다. 하나의 작업을 같은 조건에서 여러 번 실행하면 비결정적인 결과가 얼마나 흔들리는지 볼 수 있고, 도구 호출 기록을 살펴보면 실패 원인을 추적할 수 있습니다. 반면 최종 완료 판정은 가능하면 실제 파일·데이터베이스·업무 시스템의 상태에서 확인해야 합니다.

예를 들어 코딩 Agent라면 '테스트를 실행했다고 말했는가'보다 테스트가 통과했는지, 고객지원 Agent라면 '환불을 완료했다고 말했는가'보다 실제 원장과 티켓 상태가 맞는지가 중요합니다. 사실관계를 설명하는 연구 Agent라면 주장별 근거, 빠진 반대 사례, 출처의 품질까지 함께 봐야 합니다. 결과를 자동으로 채점하기 어려운 경우에는 코드 기반 검사, LLM 기반 평가, 사람의 검토를 조합할 수 있습니다. ([Anthropic, *Demystifying Evals for AI Agents*, 2026-01-09](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))

이 구분은 비용 계산에도 영향을 미칩니다. 모델 API 가격만 비교하면 작업 실패 후 재시도, 사람의 수정, 인증·통합·보안 운영의 비용을 놓칩니다. 같은 업무를 놓고 비교하려면 **검증된 완료 한 건당 총비용**을 봐야 합니다.

```text
총소유비용(TCO)
 = 개발·통합비 + 모델·도구 호출비 + 인프라 운영비
 + 평가·사람 검토비 + 보안·장애 대응비 + 이전·업그레이드비
```

기성 하네스가 언제나 몇 퍼센트 더 저렴하다는 보편적 수치는 **알 수 없습니다**. 업무의 길이, 도구 호출량, 기존 시스템 자산, 데이터 보안 조건에 따라 달라지므로 같은 조건에서 비교해야 합니다.

## 6. 언제 만들고, 언제 가져다 쓸까?

선택지를 '직접 개발 아니면 외부 서비스'라는 둘로 줄일 필요는 없습니다. 실제로는 다음과 같은 수준이 있습니다.

| 선택 | 적합한 상황 | 꼭 확인할 점 |
| --- | --- | --- |
| 현행 유지·No Agent | 기존 SQL, 규칙형 자동화, BI로 충분함 | 새로운 Agent가 실제 가치를 더하는가 |
| 단순 LLM API | 요약·분류·추출처럼 한두 번의 호출로 끝남 | 복잡한 실행 루프가 정말 필요한가 |
| Agent SDK | 기존 앱과 도구를 유지하며 실행 루프만 재사용 | SDK의 제약·업그레이드·상태 관리 방식 |
| 관리형 Harness | 장시간 실행, 샌드박스, 복구 운영 부담이 큼 | 처리 위치·보안·가격·관측 정보 이관 가능성 |
| 기존 웹앱 + Harness 결합 | 차트·Export·업무 API가 이미 있음 | UI 호환성, 로그인·권한, 이벤트 연결, 다운로드 |
| 완전 자체 Harness | 특수 실행 환경·연구 알고리즘이 제품 경쟁력의 핵심 | 공통 인프라 재구축의 실익을 증명할 수 있는가 |

여기서 '현행 유지'도 정상적인 선택입니다. 미리 정해진 규칙을 수행하는 작업이라면 LLM과 도구를 동적으로 반복 호출하는 방식이 오히려 느리거나 불안정할 수 있습니다.

예를 들어 정해진 형식의 데이터를 검증하고 결괏값을 저장하는 작업은 일반 프로그램으로 충분할 수 있습니다. 문서 초안을 순서대로 작성하고 검사하는 업무에는 미리 정해진 워크플로가 적합할 수 있습니다. 반대로 조사가 필요하고 매번 접근할 자료와 도구가 달라지는 업무는 Agent Loop의 유연성이 도움이 될 수 있습니다.

이 차이는 단순한 취향 문제가 아닙니다. **워크플로는 코드에 미리 정해진 경로를 따라가고, 에이전트는 모델이 상황에 따라 실행 경로와 도구를 선택**합니다. 경로가 정해져 있으면 재현성이 높아질 수 있고, 경로가 열려 있으면 예상하지 못한 문제를 다루기 쉽지만 통제가 어려워질 수 있습니다. Anthropic은 프롬프트 연결, 라우팅, 병렬화, 작업 위임, 평가 후 개선 같은 패턴을 제시하면서도 가장 단순한 방법부터 시작하도록 권고합니다. 프레임워크는 기본 작업을 쉽게 해주지만 추상화가 늘어나면 내부에서 무엇이 일어나는지 디버깅하기 어려워질 수 있다는 경고도 함께 제시합니다. ([Anthropic, *Building Effective Agents*, 2024-12-19](https://www.anthropic.com/engineering/building-effective-agents))

완전 자체 하네스가 합리적인 경우도 있습니다. 폐쇄망, 특수 장비, 실시간 제어, 강한 데이터 주권 요건처럼 기존 서비스가 해결하지 못하는 제약이 있을 때입니다. 실행 엔진의 도구 선택·스케줄링·문맥 제어 방식 자체가 연구 대상인 경우에도 직접 개발은 의미가 있습니다. 중요한 것은 **새로운 실행 루프를 만들 수 있는가가 아니라, 직접 소유해야 할 이유를 결과로 입증할 수 있는가**입니다.

## 이 판단이 바뀌는 조건

2026년 10월 현재 확인되는 사실은 공통 하네스, 관리형 실행, 기존 도구·UI 연결을 제공하는 기술적 선택지가 늘어났다는 것입니다. 이 사실은 공식 제품·사양에서 확인할 수 있습니다. 그러나 **기업 전체에서 자체 제작 하네스의 비율이 이미 얼마나 줄었는지는 알 수 없습니다.** 공급자의 기능 발표와 시장 점유율 자료를 혼동해서는 안 됩니다.

재사용을 우선한다는 판단도 다음 조건에서는 철회해야 합니다. 특정 업무의 실제 평가에서 기성 하네스가 지속적으로 더 낮은 완료율을 보이거나, 인증·보안·UI 연결 비용이 예상보다 크거나, 자체 런타임이 동일 조건에서 더 저렴하고 안전하다는 실측 결과가 나오는 경우입니다. 반대로 자체 개발을 유지하던 팀이라도 공통 기능의 유지보수 비용이 차별화된 성과를 넘어서면 판단을 재검토해야 합니다.

이 글은 **2026년 10월 9일**까지 확인한 자료를 기준으로 하며, 관리형 실행 제품과 UI 지원 범위가 빠르게 변하므로 **2027년 1~4월에 다시 점검**하는 것이 적절합니다.

## 마지막 판단

전용 AI 에이전트가 사라진다고 말하기는 어렵습니다. 오히려 업무별로 필요한 데이터·규칙·사용자 화면을 결합한 특화 제품은 계속 등장할 수 있습니다. 달라지는 것은 그 제품을 만들기 위해 **범용 실행 루프와 운영 인프라까지 매번 직접 구현해야 하는가**라는 질문입니다.

공통 하네스의 제품화, MCP 기반 도구 연결, UI 통합 프로토콜은 직접 개발해야 할 범위를 줄여 줍니다. 그 대신 조직이 명확하게 책임져야 할 부분—업무 데이터의 의미, 승인 정책, 공식 계산 기준, 검증된 최종 결과—은 남습니다.

따라서 새로운 에이전트를 설계할 때는 먼저 이렇게 질문하는 편이 합리적입니다. **"이 문제는 지금 있는 소프트웨어로 해결할 수 없는가? 에이전트가 필요하다면, 기존 하네스로 해결되지 않는 부분은 정확히 무엇인가?"** 그 차이가 정확성, 안전성, 총비용에서 확인될 때 자체 하네스 개발은 정당화될 수 있습니다.
