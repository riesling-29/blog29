# Agent 군단으로 PR 1000개, 가능할까요?

*Lauren Tan([@poteto](https://x.com/poteto))의 발표에서 배운, Agent를 '많이'가 아니라 '믿을 수 있게' 쓰는 법*

혹시 PR을 몇 개나 올리셨나요? 또는 Agentic 작업을 얼마나 하셨나요?

최근에 반쯤 재미로 Grok Bot을 시작했는데, Bot의 숫자가 20개가 넘어가니 "Bot을 더 늘리면 결과물도 그만큼 늘어날까?" 하는 생각이 들었습니다.

그래서 'Agent 군단을 동원해 PR 1000개 올리기'를 주제로 잡아 봤습니다. 1000이라는 숫자는 누군가의 기록이 아니라 제가 세운 목표이고, 반쯤은 농담입니다. 제가 정말 궁금했던 건 "그게 가능하려면 무엇이 먼저 준비되어 있어야 하는가"였고, 그 답을 가장 구체적으로 보여준 사람이 Lauren Tan이었습니다.

## 숫자보다 먼저 봐야 할 단서

X에서 [@poteto](https://x.com/poteto)로 활동하는 Lauren Tan은 Meta React 팀과 Netflix를 거쳐 Cursor에 합류했고(현재 SpaceX AI), 지금은 Grok Bot을 만들고 있는 엔지니어입니다.

Lauren은 발표 "How I Shipped 2000 PRs Last Month"를 "지난달 프로덕션에 PR 2,000개를 올렸다"는 말로 시작합니다. 다른 인터뷰에서는 한 달 동안 머지된 PR 2,500개, 또 다른 자리에서는 "지난달 약 1,000개"라고도 말합니다. 다만 이 숫자들은 모두 본인 발언이고, 누구나 확인할 수 있는 PR 목록이 공개된 것은 아닙니다.

제가 더 눈여겨본 건 Lauren이 스스로 붙인 단서입니다. "2,000개를 목표로 한 적은 전혀 없다." 그리고 PR 대부분이 새 기능이 아니라 리팩터링과 정리 작업이라고 밝힙니다.

![개인 Agent가 바깥의 리포트를 모아 클라우드 코디네이터에 넘기고, 코디네이터가 N개의 Agent에게 일을 나눠 작은 PR이 검증을 거쳐 머지되는 흐름](/posts/agent-army-pr-1000/agent-army-flow.svg)

*개인 Agent가 바깥의 리포트를 모아 클라우드 코디네이터에 넘기고, 코디네이터가 N개의 Agent에게 일을 나눠 작은 PR이 검증을 거쳐 머지되는 흐름*

## 핵심은 Agent의 수가 아니라 '신뢰'

발표의 주제는 한 단어, trust입니다. Lauren은 Agent를 믿지 못하는 상태에서 서브 Agent를 100개 띄우면 "slop PR과 회귀 버그만 잔뜩 생긴다"고 말합니다. 그래서 순서가 중요합니다. 아래는 Lauren이 설명한 방식입니다.

- **검증이 먼저:** Cursor 합류 초기에 Lauren은 Chrome DevTools로 성능 트레이스와 힙 스냅샷을 직접 떠서 Agent에게 넘겨줬고, 스스로를 Agent와 도구 사이의 "meat proxy"라고 불렀습니다. 그래서 처음 만든 Skill이 Agent가 직접 앱을 실행하고 트레이스를 수집하는 검증 Skill이었습니다. 매번 스크립트를 새로 짜지 않도록 CLI를 Skill 안에 두고, 앱의 기능과 진입 경로를 정리한 문서도 함께 둡니다.
- **실수를 불가능하게 만드는 코드베이스:** Agent는 코드베이스에 이미 있는 패턴을 그대로 따라 합니다. 그래서 Grok Bot 코드베이스에 Dune이라는 프레임워크를 만들어, 가장 쉬운 지름길이 곧 올바른 길이 되게 했습니다. useEffect와 일반 주석을 lint로 금지한 것도 그 예입니다. 같은 실수가 반복되면 Lint Rule부터 걸어 "출혈을 막으라"고 말합니다.
- **작게 쪼개기:** Lauren이 Agent에게 작업을 적극적으로 쪼개라고 시키는 이유는 PR 수를 늘리려는 게 아니라 커밋을 원자적으로 유지하기 위해서입니다. 4만 줄짜리 PR은 머지가 되더라도 문제가 어디서 시작됐는지 찾기가 거의 불가능하니까요.
- **두 층으로 나뉜 코디네이션:** 수천 개의 채팅창을 직접 열지 않습니다. 먼저 Slack·Linear·X 커넥터를 가진 개인 Agent(Grok Bot)가 버그 리포트를 지켜보다가 넘겨주면, Cursor Projects의 클라우드 코디네이터 Agent가 이를 받아 팀 구성을 정하고 서브 Agent에게 일을 나눠 맡깁니다. 코디네이터는 리포트를 직접 가져오지도, 직접 고치지도 않고 작업 목록을 쥐고 위임합니다. 관련 이슈 30개가 들어오면 30개를 따로 고치지 않고 묶어서 공통 원인을 찾습니다. Lauren의 설명으로는 성능, 사용자 버그 같은 영역마다 "chief of staff" 같은 코디네이터를 10개 넘게 둔다고 합니다.
- **리뷰는 샘플링, 고치는 건 환경:** 모든 PR을 사람이 미리 보지 않습니다. 머지된 기록을 샘플링해서 보고, 필요하면 revert합니다. 같은 실수가 여러 Agent에게서 보이면 그건 새 Skill, Lint Rule, 타입 제약, 검증 체크로 옮겨야 할 신호입니다.

한계도 분명히 말합니다. Lauren에 따르면 PR마다 검증 Agent를 10개 안팎으로 붙이는 full autopilot은 토큰을 많이 태우고, 되돌릴 수 없는 변경에 대해서는 "I don't really have the answer"라고 답했습니다. 결국 기준은 Agent가 그 일을 믿을 만하게 검증할 수 있느냐 하나입니다.

Lauren은 이걸 "소프트웨어 공장" 대신 "미슐랭 주방"에 비유합니다. 사람은 더 이상 재료를 직접 썰지 않지만, 주방을 어떻게 꾸릴지 정하고 최종 요리에 책임을 지는 총괄 셰프가 됩니다. X에서는 이렇게도 썼습니다. "도구를 휘두르는 사람이 여전히 책임진다."

## 실수를 고칠 자리에도 순서가 있습니다

Lauren은 Agent의 실수를 고칠 자리에도 순서가 있다고 말합니다. 먼저 코드베이스와 아키텍처로 그 실수를 아예 불가능하게 만들고, 다음은 Lint·CI 같은 정적 분석, 그 위에 Rules·리뷰 봇·Skills를 얹으라는 겁니다. 사람이 리뷰로만 지키는 스타일 가이드에만 기대지는 말라고요(발표 약 17분, 37분 무렵).

![Agent의 실수를 바로잡는 자리, 강제력이 강한 순서](/posts/agent-army-pr-1000/trust-ladder.svg)

*Agent의 실수를 바로잡는 자리, 강제력이 강한 순서: 코드베이스, 정적 분석, Rules·Skills, 스타일 가이드. 순서는 Lauren Tan 발표 기준이고, 검증을 바닥에 둔 배치는 제 정리입니다.*

## 제 Bot 팀에 옮겨 보면

여기부터는 제 경험과 생각입니다. Grok Bot을 쓰다 보면 어떤 조직의 관리자가 된 것 같다는 느낌을 받는데, Lauren의 이야기를 듣고 나니 관리자가 해야 할 일이 더 분명해졌습니다. Bot 하나하나의 결과물을 붙잡고 고쳐주는 게 아니라, Bot들이 실수하기 어려운 환경을 만드는 일입니다.

- **파트장 Bot = 코디네이터:** 비서실장·개발·리서치·영마 파트장 Bot이 요청을 받아 파트원 Bot들에게 쪼개 넘기고, 보고는 파트장 라인으로만 올라옵니다. 제가 Bot마다 지시를 복붙하는 일을 줄이려는 구조입니다.
- **"두 번 말하면 규칙으로":** 같은 지적을 두 번 하게 되면 대화로 다시 말하지 않고 Skill이나 규칙 문서로 옮깁니다.
- **코드가 아닌 일에도 검증을:** 리서치와 마케팅 Bot의 결과물에는 출처 URL을 반드시 붙이게 합니다. 이 글도 그렇게 만들었습니다. 출처가 없는 숫자는 쓰지 않는 게 원칙입니다.

이번 주에 저부터 해 보려는 것들입니다.

- **병목 기록:** 이번 주에 내가 Agent에게 옮겨 준 것(에러 로그, 스크린샷 설명, 고객 메시지)을 적어 보기. Lauren이 반복해서 던지는 질문은 "내가 아직 어디서 병목인가?"입니다.
- **검증 Skill 하나:** Agent가 스스로 앱을 실행하고, 결과를 보고, 증거를 남기는 가장 작은 루프 만들기.
- **반복 실수 하나를 막기:** 가장 자주 고쳐준 패턴 하나를 골라 Lint Rule이나 Skill·규칙 문서로 옮기기.
- **PR 쪼개기 규칙:** "PR 하나에 변경 하나"를 Agent 지침에 넣기.
- **샘플링 리뷰:** 하루 한 번, 머지된 기록 몇 개를 골라 보고 반복되는 패턴 찾기.
- **되돌릴 수 있는 일부터:** 쉽게 revert할 수 있는 작업부터 자율에 맡기고, 되돌리기 어려운 작업은 사람 승인을 남겨 두기.

여러분의 Agent는 지난달 PR을 몇 개 올렸나요? 어떤 Lint Rule이나 Skill로 어떤 실수를 막으셨는지 답글로 나눠 주시면 반갑겠습니다. 다만 사례를 나눌 때는 회사 소스 코드, API 키, 고객 정보, 내부 시스템 주소는 빼 주세요. Agent에게 머지나 배포 권한을 줄 때도 권한 범위를 최소로 잡고, 되돌릴 수 있는 경로를 먼저 마련해 두시길 권합니다.
