혹시 PR을 몇 개나 올리셨나요? Agentic 작업은 얼마나 하셨나요?

반쯤 재미로 Grok Bot을 시작했는데, Bot이 20개를 넘자 궁금해졌습니다. Bot을 늘리면 결과물도 그만큼 늘어날까?

그래서 'PR 1000개'를 목표로 잡아 봤습니다. 반쯤 농담입니다. 진짜 질문은 이것이었습니다.

> **그게 가능하려면, 무엇이 먼저 있어야 할까?**

가장 구체적인 답을 준 사람이 Lauren Tan입니다.

## Lauren Tan은 누구인가

| | |
|---|---|
| X | [@poteto](https://x.com/poteto) |
| 경력 | Meta React 팀, Netflix, Cursor(현재 SpaceX AI) |
| 지금 하는 일 | Grok Bot을 만드는 엔지니어 |
| 발표 | "How I Shipped 2000 PRs Last Month" |

Lauren은 "지난달 PR 2,000개를 올렸다"는 말로 발표를 시작합니다. 다른 인터뷰에서는 2,500개, 약 1,000개라고도 했습니다. 모두 본인 발언이고, 공개된 PR 목록은 없습니다.

숫자보다 중요한 건 본인이 붙인 단서입니다.

> "2,000개를 목표로 한 적은 전혀 없다."
>
> 그리고 PR 대부분은 새 기능이 아니라 리팩터링과 정리 작업입니다.

![개인 Agent가 리포트를 모아 클라우드 코디네이터에 넘기고, 코디네이터가 N개의 Agent에게 일을 나눠 작은 PR이 검증을 거쳐 머지되는 흐름](/posts/agent-army-pr-1000/agent-army-flow.svg)

## 핵심은 Agent의 수가 아니라 신뢰

> 💡 **한 줄 요약**
> 믿지 못하는 Agent를 100개 띄우면, 쌓이는 건 slop PR과 회귀 버그뿐입니다.

그래서 순서가 중요합니다. Lauren이 말한 다섯 가지입니다.

**1. 검증이 먼저**
처음엔 Lauren이 직접 성능 트레이스를 떠서 Agent에게 넘겼습니다. 스스로를 "meat proxy"라고 불렀죠. 그래서 첫 Skill은 Agent가 직접 앱을 실행하고 트레이스를 모으는 검증 Skill이었습니다.

**2. 실수가 불가능한 코드베이스**
Agent는 코드베이스의 패턴을 그대로 따라 합니다. 그래서 가장 쉬운 길이 곧 올바른 길이 되게 만듭니다. 같은 실수가 반복되면 Lint Rule부터 겁니다.

**3. 작게 쪼개기**
목적은 PR 수가 아니라 원자적인 커밋입니다. 4만 줄짜리 PR은 문제가 어디서 시작됐는지 찾을 수 없습니다.

**4. 두 층의 코디네이션**
개인 Agent가 Slack·Linear·X에서 버그 리포트를 모아 넘기면, 클라우드 코디네이터가 받아서 서브 Agent에게 나눠 맡깁니다. 비슷한 이슈 30개는 묶어서 공통 원인을 찾습니다.

**5. 리뷰는 샘플링, 고치는 건 환경**
모든 PR을 사람이 보지 않습니다. 머지된 것 일부를 보고 필요하면 revert합니다. 같은 실수가 여러 번 보이면 Skill이나 Lint Rule로 옮깁니다.

> ⚠️ **한계도 있습니다**
> PR마다 검증 Agent를 10개씩 붙이면 토큰이 많이 듭니다. 되돌릴 수 없는 변경에 대해서는 Lauren도 "I don't really have the answer"라고 답했습니다.

Lauren의 비유는 이렇습니다.

> 🍳 소프트웨어 공장이 아니라 **미슐랭 주방**.
> 사람은 재료를 직접 썰지 않지만, 주방을 꾸리고 최종 요리에 책임지는 총괄 셰프입니다.

## 실수를 막는 자리에도 순서가 있다

강제력이 강한 곳부터 막으라는 겁니다.

1. **코드베이스·아키텍처**: 실수 자체가 불가능하게
2. **Lint·CI**: 정적 분석으로 걸러내기
3. **Rules·리뷰 봇·Skills**: 그 위에 얹기
4. **스타일 가이드**: 사람 리뷰에만 기대는 건 마지막

![Agent의 실수를 바로잡는 자리, 강제력이 강한 순서](/posts/agent-army-pr-1000/trust-ladder.svg)

*순서는 Lauren Tan 발표 기준이고, 검증을 바닥에 둔 배치는 제 정리입니다.*

## 제 Bot 팀에 옮겨 보면

Bot이 많아지면 관리자가 된 기분이 듭니다. Lauren의 이야기로 관리자의 일이 분명해졌습니다.

> **Bot의 결과물을 하나하나 고치는 게 아니라, 실수하기 어려운 환경을 만드는 것.**

| Lauren의 방식 | 제 Bot 팀 |
|---|---|
| 코디네이터 Agent | 파트장 Bot이 요청을 쪼개 파트원에게 넘김 |
| 반복 실수는 Lint Rule로 | 같은 말을 두 번 하면 Skill·규칙 문서로 |
| 검증 Skill | 리서치·마케팅 결과물에 출처 URL 필수 |

## 이번 주 체크리스트

- [ ] 내가 Agent에게 옮겨 준 것(에러 로그, 스크린샷, 고객 메시지) 적어 보기
- [ ] Agent가 스스로 실행하고 증거를 남기는 가장 작은 검증 Skill 만들기
- [ ] 가장 자주 고쳐준 실수 하나를 Lint Rule이나 Skill로 옮기기
- [ ] "PR 하나에 변경 하나"를 Agent 지침에 넣기
- [ ] 하루 한 번, 머지된 기록 몇 개를 샘플링해 보기
- [ ] 되돌릴 수 있는 일부터 자율에 맡기기
