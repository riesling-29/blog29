## 1. 시작: "모델은 이미 말을 잘하는데 왜 자동화는 생각보다 어렵나?"

TypeSafe의 창업자가 Jev 발표문에서 먼저 건넨 질문은 이렇다. LLM은 사람에게 전달할 텍스트를 만드는 데 최적화되어 있다. 그런데 소프트웨어 내부에서는 수많은 순간마다 실제로 필요한 것이 긴 문장이 아니다.

* 어느 tool을 쓸 것인가
* 계속할 것인가
* 멈출 것인가
* 사람이 봐야 하는가
* 위험도는 어느 정도인가

이런 판단은 "잘 말한 문장"이 아니라, 프로그램이 바로 처리할 수 있는 값이다. TypeSafe는 이 문제를 Jev라는 모델로 접근한다.

Jev의 입출력을 TypeSafe의 표현 그대로 쓰면, **unstructured state in → typed probabilistic decisions out**이다. 쉬운 말로 풀어면, 정리되지 않은 상태(문자열이나 JSON)를 넣고, 타입이 정해진 확률적 판단을 낸다. "이 문의는 배송 조회가 0.78, 해당 없음이 0.12" 같은 값이 나오는 식이다. 문장을 쓰는 일과 다음 일을 고르는 일이 같은 출력이 아니라는 것, 그게 출발점이다.

## 2. System One Model이라는 발상

Jev는 TypeSafe가 **System One model**이라고 부르는 계열이다. 이름은 Kahneman의 System 1 / System 2에서 가져왔다. 단, 인간 인지과학 모델과 AI 구조가 동일하다는 주장이 아니다. 이름의 유래일 뿐이다.

대비를 이렇게 놓는다.

| | 역할 |
|---|---|
| **System 2** | GPT·Claude 같은 reasoning·generation 모델. 분석, 계획, 코드, 글쓰기, 어려운 문제 |
| **System 1** | Jev가 목표로 하는 영역. 분류, routing, scoring, gating, stop/retry 같은 반복적이고 제한된 판단 |

여기서 핵심은 "Jev가 GPT를 대체한다"가 아니다. **"에이전트 내부의 모든 판단까지 GPT에게 맡길 필요가 있는가?"**라는 질문이다. 어려운 추론은 System 2에, 반복되는 작은 판단은 System 1에, 이렇게 나눌 수 있다면 그 작은 판단을 따로 최적화할 이유가 생긴다.

## 3. 실제로 Jev에 무엇을 보내는가

하나의 에이전트 예를 붙인다. 사용자가 "배송이 아직 안 왔습니다. 어디까지 왔는지 확인해 주세요"라고 물었다고 하자.

```text
state:
  현재 사용자 요청 + 필요한 최소 context (주문 정보, 배송 상태)

questions:
  - 어떤 tool을 쓸 것인가?
  - 이 요청이 위험한가?
  - human review가 필요한가?
```

`state`는 판단에 필요한 자료다. 문자열이나 JSON이면 된다. `questions`는 그 자료에 대해 묻는 질문이다. 한 요청의 질문들은 같은 상태를 보지만 각각 따로 평가된다. 이 세 가지 질문 형식이 Jev의 핵심이다.

**Choice** — 후보 중 하나를 고르는 상대적 판단. "이 문의는 배송 조회인가, 교환·반품인가, 결제인가, 해당 없음인가"처럼, 정해 둔 후보 집합 안에서 확률을 배분한다.

**Score** — 서술된 단계들 사이에서 정도를 평가. "이 장애는 어느 심각도 단계인가"처럼, 순서가 있는 단계 설명을 주고 각 단계의 확률을 단계 번호와 가중합한 점수가 나온다. 빈칸에 임의 숫자를 쓰는 기능이 아니다.

**Noul** — 하나의 명제가 참인지에 대한 확률적 판단. "이 메시지에 환불 요청이 있는가"처럼 yes일 확률을 반환한다.

Choice가 특히 중요한 이유를 하나 더 붙인다. Choice는 항상 후보 중 확률을 배분하기 때문에, "아무 것도 하지 않는다"라는 절대적 판단이 별도로 필요할 수 있다. 목록 밖의 입력이 있을 수 있으면 `other`, `none`, `insufficient_information`처럼 의미가 명확한 후보를 설계해야 한다.

## 4. "이거 그냥 classifier 아닌가?"

이 반론은 정면으로 다뤄야 한다. Parallel은 Jev를 **"BERT + classification head를 써봤다면 익숙할 것"**이라고 표현했다. 입출력이 닮았다는 비유다.

그러나 차이는 있다.

| | 접근 |
|---|---|
| **전용 classifier** | 특정 task의 데이터를 수집 → 라벨을 붙여 → 학습 → serving. 하나의 작업에 특화한다. |
| **Jev** | request time에 자연어 question과 candidate를 지정해, task-specific fine-tuning 없이 여러 bounded decision을 수행하려는 모델. |

즉, 전용 분류기는 "이 작업"을 위해 데이터를 모아서 학습하는 반면, Jev는 "이번 요청에 이 후보를 줘"라고 매번 지정하는 방향으로 설계됐다.

다만 여기서 정확히 해야 할 점이 있다. 기존에도 zero-shot classifier가 존재했고, LLM도 structured output을 반환할 수 있다. Hugging Face의 NLI 기반 zero-shot classification은 실행 시 후보 라벨을 지정할 수 있다. 따라서 "Jev가 분류나 JSON 출력을 최초로 발명했다"는 식으로 쓰면 안 된다.

핵심은 기능의 최초 발명이 아니라, **decision을 독립된 model/API primitive로 최적화했다는 제품·연구 방향**에 있다.

## 5. Rule / Classifier / Jev / LLM 비교

이 비교는 본문에서 반드시 필요하다.

| 축 | Code / Rule | 전용 classifier | Jev | LLM (reasoning) |
|---|---|---|---|---|
| deterministic 계산 | 강점 | 제한적 | 제한적 | 취약 |
| task-specific training | 불필요 | 필수 | 불필요 | 불필요 |
| runtime에 후보 변경 | 코드 수정 | 재학습 | 가능 | 가능 |
| probability output | 없음 | 있음 | 있음 | 있음 (structured output) |
| 자유 생성 | 없음 | 없음 | 없음 | 강점 |
| 복잡한 reasoning | 없음 | 없음 | 제한적 | 강점 |
| latency/cost | 가장 낮음 | 낮음 | 낮음 (제작사 주장) | 가장 높음 |
| 대표 사용처 | 날짜·권한·중복 확인 | 특화 작업 | 반복적 bounded decision | 추론·생성 |

이 표에서 "아무 AI도 쓰지 않고 code/rule을 유지한다"는 정상적인 대안이다. 날짜 계산, 권한 검사, 중복 실행 확인처럼 코드로 정확히 해결 가능한 문제를 Jev에게 넘기는 것을 권하지 않는다. 의미 해석이 필요 없는 단계까지 AI로 바꾸면 추가 호출의 편익이 없을 수도 있다.

## 6. Agent에서 왜 흥미로운가

이 부분이 이번 글의 핵심이다.

기존 에이전트는 이렇게 돌아간다.

```text
User
  → LLM
  → LLM이 reasoning
  → tool 선택
  → tool 실행
  → LLM
  → 계속/중단 판단
  → ...
```

매 턴마다 reasoning LLM이 호출된다. tool을 고르는 일, 계속할지 멈출지 결정하는 일, 위험도를 재확인하는 일까지 전부 같은 큰 모델이 한다.

대안은 이렇게 나눈다.

```text
State
  → 작은 bounded decision (Jev 등)
  → 확실하면 Tool / Stop / Retry
  → 어렵거나 애매하면 reasoning LLM
  → 실행은 code/policy가 통제
```

여기서 Jev는 "에이전트의 brain 전체"가 아니다. **reflex / router / gate / decision layer** 정도다. 반사처럼 빠르게, 제한된 후보 안에서 판단을 하고, 애매한 것만 reasoning LLM으로 넘긴다.

Vercel이 제시한 용도가 이 구조를 실물로 보여준다.

* 다음 tool / subagent 선택
* continue / retry / ask / stop
* urgency / risk 평가
* guardrails
* human escalation

이 다섯 가지가 바로 "반복적이고 제한된 판단"이다. 매번 LLM을 부르기보다, 이 판단을 전용 계층으로 처리하면 지연과 비용이 줄고, 실행 통제는 code/policy가 담당한다.

## 7. Hermes 사례

TypeSafe의 **Skill suggestion cookbook**을 별도 사례로 다룬다.

Nous Research Hermes의 특정 커밋 skill 목록 182개를 대상으로 한 구조다.

1차: 전체 182 skill을 얕게 평가. 필요한 skill 자체가 있는지도 함께 판단한다.
2차: 상위 3개만 자세히 읽고 다시 평가.

결과는 한 개를 추천하거나, 아무 것도 추천하지 않을 수 있다.

TypeSafe가 공개한 488-request 실험 수치:

| 지표 | 개선 전 | 개선 후 |
|---|---|---|
| wrong skill | 16.8% | 7.3% |
| skill이 필요 없는데 load | 9.8% | 4.0% |
| 정답 skill을 직접 알려준 조건 | 2.5% | 1.2% |

이것은 **TypeSafe 자체 실험**이다. `claude-haiku-4-5-20251001`을 사용한 단일 턴 요청 488개에 대한 결과다. 전체 에이전트 성공률이나 사용자의 현재 Hermes 환경 결과로 일반화하면 안 된다.

이 사례의 의미는 숫자 자체보다, **"큰 LLM 앞에 작은 decision layer를 넣는다"는 실제 구조**를 보여주는 데 있다. 추론 모델 전체를 바꾸지 않고, 어떤 지침을 읽을지 보조하는 작은 판단을 앞에 붙였다.

## 8. 왜 이름이 Jev인가

이름은 William Stanley Jevons와 Jevons paradox에서 가져왔다. Jevons paradox는, 어떤 재화의 가격이 크게 내려가면 오히려 수요가 늘어서 총 소비가 증가하는 현상을 가리킨다.

TypeSafe의 thesis를 이 이름에 붙여 풀어면: AI intelligence의 단가가 크게 낮아지면, 기존 작업을 싸게 하는 데 그치지 않고, **지금은 AI를 호출하지 않던 수많은 작은 판단에도 intelligence가 사용될 수 있다.**

이것이 Jev가 단순한 classifier API 이상을 주장하는 이유다. "작은 판단에 AI를 쓰는 것" 자체가 새로운 수요를 만든다는 것이다.

## 9. 발표 직후 왜 화제가 되었나

| 날짜 | 사건 |
|---|---|
| 2026-09-15 | TypeSafe가 Jev early access를 발표 |
| 2026-09-16 | Vercel이 AI Gateway 제공을 공지 |
| 2026-09-17 | LangChain이 Jev를 harness에 연결하는 글을 공개 |
| 2026-09-18 | Vercel이 첫 24시간 유료 팀 약 13% 사용을 보고 |
| 2026-09-18 | Parallel이 자체 검색·분류 작업의 외부 테스트를 공개 |

Vercel 수치는 **Vercel AI Gateway 내부의 초기 adoption**이다. 전체 시장 점유율이 아니다. "모두가 갈아타고 있다"가 아니라, "연동 소개와 초기 사용 보고가 빠르게 나왔다" 정도로 범위를 제한한다.

## 10. 성능은 아직 이렇게 봐야 한다

TypeSafe의 자체 workflow benchmark에서 **193.6배 빠름, 444.6배 저렴함**을 제시한다. 이것은 **vendor benchmark**다. 기준은 정답 라벨만이 아니라 외부 대형 모델들의 참조 확률이며, 비교 LLM에는 확률까지 반환하도록 한 wrapper를 사용했다. 평가 작업은 회사 내부에서 구성됐다.

바로 옆에 Parallel의 외부 테스트를 붙인다.

* reranking: NDCG@10 0.7, 내부 시스템 중 하나와 유사
* topic classification: 자체 특화 모델이 우세
* freshness classification: 자체 특화 모델이 우세
* 자체 인프라를 가진 Parallel에서는 Jev의 문서당 비용이 더 높았음

따라서 "LLM보다 수백 배 빠르니 모든 classifier를 교체한다"가 아니다. **"전용 classifier를 만들 만큼 데이터와 인프라가 없는 bounded decision에서는 상당히 흥미로운 zero-shot starting point"**라는 식으로 정리한다.

## 11. 한계

* 정밀 산술·날짜 계산에 부적합할 수 있다.
* irrelevant context가 많으면 품질이 저하될 수 있다.
* adversarial input / prompt injection 해결책이 아니다. 구조화된 출력이 injection 방어를 보장하지 않는다.
* typed output이라고 의미상 정답이 보장되는 것은 아니다.
* confidence를 실제 정답률로 직접 해석하지 않는다.
* 한국어 production calibration은 현재 확인되지 않는다.

## 12. 마지막 결론

Jev의 의미는 "또 하나의 더 똑똑한 LLM"이 등장했다는 데 있지 않다. AI 에이전트를 하나의 거대한 생성 모델에 맡기는 대신,

* code는 계산하고
* decision model은 판단하고
* reasoning model은 어려운 문제를 풀고
* human은 필요한 경우 개입하는

분업형 architecture가 현실적인 선택지가 되고 있다는 점에 있다.

Jev가 그 자리를 차지할지는 아직 검증이 필요하다. 하지만 "모든 AI 작업이 text generation일 필요는 없다"는 문제 제기는 충분히 주목할 가치가 있다.
