## 먼저 요약

OCEL(Object-Centric Event Log) 2.0은 하나의 이벤트가 여러 종류의 객체와 동시에 관계를 맺을 수 있도록 만든 객체 중심 이벤트 로그 표준이다. 주문 처리에서 `출고 완료`라는 이벤트가 주문, 상품, 포장, 작업자와 함께 관련되는 상황을 한 로그 안에 표현할 수 있다.

OCEL 2.0의 핵심은 다음 네 가지다.

- 이벤트와 객체를 별도로 정의한다.
- 이벤트-객체(E2O) 관계와 객체-객체(O2O) 관계를 기록한다.
- 관계에 한정자(qualifier)를 붙여 그 의미를 구분한다.
- 객체 속성이 시간에 따라 바뀌는 이력을 보존한다.

공식 OCEL 2.0 규격은 JSON, XML, SQLite의 세 가지 교환 형식을 정의한다. 어떤 형식을 선택하더라도 같은 개념 모델을 표현하는 것이 목적이다.

## 왜 객체 중심 로그가 필요한가

전통적인 프로세스 마이닝 로그는 보통 주문 번호나 고객 번호처럼 하나의 케이스 식별자를 기준으로 이벤트를 나열한다. 분석 질문과 케이스 기준이 정확히 일치하면 이 구조는 단순하고 효과적이다.

문제는 실제 업무가 한 가지 객체만을 중심으로 움직이지 않는다는 점이다. 하나의 주문에 여러 상품과 배송이 연결되고, 하나의 배송에 여러 주문이 합쳐질 수도 있다. 이 데이터를 주문 기준으로만 평탄화하면 같은 배송 이벤트가 여러 번 복제될 수 있고, 배송 기준으로 평탄화하면 주문별 흐름이 끊길 수 있다. 객체 중심 로그는 처음부터 여러 객체를 유지하여 이런 정보 손실이나 중복 가능성을 줄이려는 접근이다.

다만 모든 로그에 OCEL이 필요한 것은 아니다. 분석 질문이 안정적인 단일 케이스에 한정되고 평탄화로 관계가 왜곡되지 않는다면 기존 케이스 중심 로그를 유지하는 것이 더 경제적일 수 있다.

## OCEL 2.0의 기본 구조

OCEL 2.0 로그는 이벤트 타입, 객체 타입, 이벤트, 객체와 그 사이의 관계로 구성된다.

| 요소 | 의미 | 예시 |
| --- | --- | --- |
| 이벤트 타입 | 발생한 활동의 종류 | 주문 생성, 결제, 출고 |
| 객체 타입 | 업무 개체의 종류 | 주문, 상품, 배송, 작업자 |
| 이벤트 | 특정 시각에 발생한 활동 | 2026-08-04 09:30의 출고 완료 |
| 객체 | 고유 식별자를 가진 업무 개체 | 주문 `O-17`, 배송 `S-3` |
| E2O 관계 | 이벤트와 관련 객체의 연결 | 출고 완료 → 배송 `S-3` |
| O2O 관계 | 객체와 객체의 연결 | 주문 `O-17` → 상품 `I-8` |
| 한정자 | 관계가 담당하는 역할이나 의미 | `shipment`, `item`, `forwarder` |

이벤트는 타입, 시각, 속성, 객체 관계를 가진다. 객체는 타입, 속성 이력, 다른 객체와의 관계를 가진다. 한 이벤트가 참조할 수 있는 객체의 수와 타입은 하나로 제한되지 않는다.

한정자 이름은 표준이 업무별 어휘를 대신 정해주는 방식이 아니다. 따라서 같은 의미를 `item`, `product`, `line-item`처럼 제각각 기록하지 않도록 조직이나 데이터 제품 차원에서 어휘를 관리해야 한다.

## OCEL 1.0에서 달라진 점

OCEL 2.0 규격이 1.0보다 명시적으로 확장한 부분은 다음과 같다.

1. **객체 간 관계(O2O)**: 주문이 상품을 포함하거나 배송이 주문에 속하는 관계를 로그 자체에 기록할 수 있다.
2. **관계 한정자**: 이벤트-객체와 객체-객체 관계에 역할을 붙일 수 있다. 같은 이벤트에 여러 작업자가 연결되더라도 담당자와 승인자를 구분할 수 있다.
3. **시간에 따른 객체 속성 변화**: 가격, 상태, 담당 부서처럼 바뀔 수 있는 값을 변경 시각과 함께 보존할 수 있다.

공식 저자들은 이러한 확장이 OCEL 1.0의 표현력 한계를 보완한다고 설명한다. 다만 실제 분석 품질이 자동으로 좋아진다는 뜻은 아니다. 원천 시스템에서 관계와 변경 이력을 정확히 추출하지 못하면 더 풍부한 스키마가 오히려 불완전한 데이터를 정교하게 보이게 만들 수 있다.

## 간단한 JSON 예시

아래 예시는 `출고` 이벤트가 주문과 배송, 작업자 객체를 서로 다른 역할로 참조하는 최소 형태를 보여준다. 한정자 어휘는 설명을 위해 임의로 정했다.

```json
{
  "eventTypes": [
    { "name": "dispatch", "attributes": [] }
  ],
  "objectTypes": [
    { "name": "order", "attributes": [] },
    { "name": "shipment", "attributes": [] },
    { "name": "employee", "attributes": [] }
  ],
  "events": [
    {
      "id": "e-100",
      "type": "dispatch",
      "time": "2026-08-04T00:30:00Z",
      "attributes": [],
      "relationships": [
        { "objectId": "o-17", "qualifier": "order" },
        { "objectId": "s-3", "qualifier": "shipment" },
        { "objectId": "u-2", "qualifier": "forwarder" }
      ]
    }
  ],
  "objects": [
    { "id": "o-17", "type": "order", "attributes": [], "relationships": [] },
    { "id": "s-3", "type": "shipment", "attributes": [], "relationships": [] },
    { "id": "u-2", "type": "employee", "attributes": [], "relationships": [] }
  ]
}
```

실제 로그에서는 각 타입의 속성 정의와 객체 속성 값, 필요한 O2O 관계를 추가한다. 객체 속성에는 값과 함께 적용 시각을 기록할 수 있으므로 분석 시점에 맞는 상태를 재구성할 수 있다.

## 세 가지 공식 교환 형식

OCEL 2.0의 개념 모델은 같지만 저장 방식의 장단점은 다르다.

- **JSON**은 구조를 눈으로 읽기 쉽고 웹 및 데이터 파이프라인에서 다루기 편하다. 공식 JSON Schema로 구조를 검증할 수 있다.
- **XML**은 XSD 기반 검증이나 기존 XML 도구 체계와 결합할 때 유리하다.
- **SQLite**는 관계형 테이블로 저장하며 SQL 조회와 큰 로그의 부분 접근에 적합하다. 이벤트-객체, 객체-객체 관계와 타입별 속성 테이블을 분리한다.

위의 적합성 평가는 형식의 기술적 특성에서 도출한 실무적 판단이다. 실제 처리 성능의 우열은 로그 크기, 쿼리, 라이브러리 구현과 하드웨어에 따라 달라지므로 일반적인 수치로 확정할 수 없다.

현재 공식 사이트에는 CSV나 Parquet 관련 자료도 보이지만, 이는 OCEL 2.1 직렬화 확장과 함께 확인해야 한다. OCEL 2.0 자체의 공식 교환 형식을 설명할 때는 JSON, XML, SQLite 세 가지를 기준으로 삼는 편이 버전 혼동을 피할 수 있다.

## 데이터 설계에서 주의할 점

### 1. 객체 경계를 분석 질문보다 먼저 검토한다

데이터베이스 테이블 하나를 객체 타입 하나로 그대로 옮기면 기술적 저장 구조가 업무 개념을 대신할 수 있다. 독립적인 생명주기와 식별자, 다른 객체와의 관계가 있는지를 기준으로 객체 후보를 검토해야 한다.

### 2. 식별자를 안정적으로 관리한다

이벤트 집합 안의 이벤트 ID와 객체 집합 안의 객체 ID는 각각 일관되게 고유해야 한다. 서로 다른 원천 시스템의 키가 충돌할 가능성이 있다면 시스템 구분자를 포함한 식별자 규칙이 필요하다.

### 3. 한정자 어휘를 통제한다

한정자가 자유 문자열처럼 운영되면 같은 관계가 여러 이름으로 갈라진다. 허용 목록, 정의, 작성 책임자와 변경 절차를 함께 관리하는 편이 좋다.

### 4. 시간의 의미를 명시한다

이벤트 시각이 업무 발생 시각인지 시스템 기록 시각인지 구분하고 시간대 정책을 정해야 한다. 객체 속성 변경 시각도 원천 데이터가 실제로 제공하는 범위만 기록해야 한다. 이력이 없는 값을 추정해 넣었다면 관측값과 추정값을 구분해야 한다.

### 5. 스키마 검증과 의미 검증을 분리한다

공식 JSON Schema나 XML XSD는 파일 구조와 데이터 타입 오류를 찾는 데 도움이 된다. 그러나 `forwarder`가 정말 출고 담당자를 가리키는지, 누락된 객체가 없는지까지 보장하지는 않는다. 형식 검증과 업무 규칙 검증이 모두 필요하다.

## 언제 도입할 만한가

다음 조건이 반복해서 나타난다면 OCEL 2.0을 검토할 근거가 있다.

- 하나의 이벤트가 여러 종류의 업무 객체에 동시에 영향을 준다.
- 분석 관점마다 로그를 다시 추출하거나 이벤트를 복제하고 있다.
- 객체 간 관계 자체가 분석 대상이다.
- 객체 속성의 변화 시점을 보존해야 한다.
- 여러 프로세스 관점을 한 데이터 모델에서 연결하려 한다.

반대로 단일 케이스의 순차 흐름만 필요하고 객체 관계나 속성 이력이 분석 결과를 바꾸지 않는다면, 아무것도 바꾸지 않고 기존 로그를 유지하는 선택도 타당하다. OCEL 도입에는 객체 모델 합의, 추출 로직, 품질 검사, 도구 호환성 관리 비용이 추가되기 때문이다.

## 확인된 사실과 도입 판단

**확인된 사실:** OCEL 2.0 규격은 이벤트가 서로 다른 타입의 여러 객체를 참조하게 하며, 명시적 O2O 관계, E2O·O2O 한정자, 시간에 따른 객체 속성 변경을 지원한다. 규격 문서의 버전 날짜는 2023년 10월 16일이고 공식 교환 형식은 JSON, XML, SQLite다.

**도입 판단:** 여러 객체가 얽힌 업무를 케이스 하나로 평탄화하면서 중복이나 연결 손실이 발생하는 조직에는 OCEL 2.0이 유력한 데이터 모델 후보다. 이 판단의 근거는 위 기능들이 바로 다중 객체 관계와 변경 이력을 보존하기 위해 설계되었다는 점이다. 그러나 해당 문제가 실제 데이터에서 관측되지 않거나, 필요한 관계를 원천 시스템에서 신뢰성 있게 추출할 수 없다면 이 판단을 철회해야 한다.

## 반증 조건과 유효기간

이 글의 사실 설명은 OCEL 2.0 공식 규격과 관련 원 논문을 2026년 8월 4일에 확인한 결과다. 이후 OCEL 표준의 새 버전이 확정되거나 공식 직렬화 형식과 호환성 규칙이 변경되면 해당 부분을 다시 검증해야 한다.

OCEL 도입이 적합하다는 판단은 다음 중 하나가 확인되면 철회하거나 보류한다.

- 실제 분석 질문이 단일 케이스 로그만으로 손실 없이 해결된다.
- 객체 관계 또는 속성 변경 이력의 정확도를 검증할 수 없다.
- 사용하려는 분석 도구가 필요한 OCEL 2.0 기능이나 형식을 지원하지 않는다.
- 추출·운영 비용이 관점별 재작업과 오류 감소에서 얻는 이익보다 크다.

마지막 항목의 비용과 이익은 조직별 측정 자료가 없으므로 현재로서는 알 수 없음이다. 파일 규모나 처리 속도 역시 구현과 환경에 따라 달라 일반화된 수치로 제시하지 않는다.
