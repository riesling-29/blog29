Attention과 KV Cache를 학습한 뒤에는 다음 질문이 자연스럽게 이어집니다.
“LLM은 입력을 받아 다음 토큰을 만드는 모델인데, 어떻게 코드를 고치고 테스트까지 실행할 수 있을까요? 모델 안에 터미널이 있는 걸까요?”

답은 모델과 그 주변 프로그램이 주고받는 과정에 있습니다. LLM은 매 단계에서 현재 입력과 함께 전달된 도구 설명을 바탕으로 다음 출력을 생성합니다. 일반적인 질문에는 답변 문장을 만들고, 도구가 필요하다고 판단하면 사용할 도구의 이름과 인자를 담은 구조화된 호출을 출력합니다. 여기까지가 모델의 출력입니다. 이 호출 자체가 명령을 실행하는 것은 아닙니다. 하네스가 호출 형식과 권한을 확인한 뒤 해당 도구를 실행하고, 파일 내용이나 명령 결과를 다음 입력에 포함해 모델을 다시 호출합니다. 모델은 결과를 바탕으로 답변을 마치거나 다른 도구 호출을 이어 갑니다. 따라서 “모델이 행동한다”는 말은 실행할 행동을 선택해 요청을 출력한다는 뜻이며, 파일 수정이나 명령 실행처럼 환경을 실제로 바꾸는 일은 연결된 도구와 실행기가 맡습니다. 이런 호출·실행·결과 반영이 반복되어 목표를 수행하는 시스템을 AI 에이전트라고 설명할 수 있습니다.

에이전트의 범위는 자료마다 다릅니다. WEF가 2024년 6월 중국 다롄에서 개최한 Annual Meeting of the New Champions의 ‘What Can AI Assistants Do?’ 세션은 AI 에이전트의 활용과 인간·기계의 관계를 논의한 패널 토론이었습니다. [WEF가 이 세션을 정리한 기사](https://www.weforum.org/stories/technological-innovation/what-is-an-ai-agent-experts-explain/)에서도 전문가들은 서로 다른 측면을 강조합니다. Vanderbilt University의 Xi Kang은 일반 사용자도 접근할 수 있는 AI 기반 예측·의사결정 지원까지 폭넓게 봅니다. Neusoft의 Liu Jiren은 환경을 감지하고 자율적으로 판단·행동하는 점을 중요하게 봅니다. Moonhub의 Nancy Xu는 LLM에 행위 능력을 더하는 흐름으로 설명하며, 개인의 디지털 동반자나 기업의 디지털 직원에 비유합니다. causaLens의 Darko Matovski는 업무에 따라 자율성과 인간의 통제 사이 경계를 정하고, 사람이 에이전트의 작업 흐름을 감독할 지점을 고려해야 한다고 봅니다. 이 설명들은 하나의 엄밀한 정의에 합의했다기보다, 의사결정 지원부터 환경을 감지해 자율적으로 행동하는 시스템까지 ‘에이전트’라는 말이 넓게 쓰이고 있음을 보여줍니다. 어떤 시스템을 에이전트라고 부를지는 자율성, 실제 행동, 사람의 감독을 어디까지 포함하느냐에 따라 달라집니다. [WEF의 전문가 패널 기사](https://www.weforum.org/stories/technological-innovation/what-is-an-ai-agent-experts-explain/)

## Attention에서 에이전트로

LLM은 입력된 토큰을 바탕으로 다음 출력을 만듭니다. Attention은 지금 처리하는 토큰이 앞선 맥락의 어느 부분을 참고할지 계산하는 데 쓰입니다. KV Cache는 이미 처리한 토큰의 key와 value를 생성 과정에서 재활용해 매번 다시 계산하는 일을 줄입니다. Attention과 KV Cache는 모델이 입력 맥락을 처리하고 다음 토큰을 생성하는 계산 방식에 속합니다. [Hugging Face의 캐시 설명](https://huggingface.co/docs/transformers/main/cache_explanation/)을 떠올리면 됩니다.

하지만 KV Cache가 파일을 열거나, 어제의 작업을 영구히 기억하거나, 테스트 결과를 알아서 가져오는 것은 아닙니다. 대화 이력과 파일, 도구 결과 중 무엇을 다음 호출에 넣을지는 모델 바깥의 시스템이 관리합니다. 서비스에 따라 맥락을 다시 구성할 수도 있고 일부 계산을 재활용할 수도 있습니다. KV Cache는 토큰 생성에 필요한 계산을 재사용하고, 에이전트의 작업 기억은 다음 호출에 넣을 맥락을 관리합니다. 둘은 역할이 다릅니다.

ChatGPT나 Claude 같은 AI 서비스에는 모델 외에도 이미지·음성 입력, 검색·코드 실행 도구가 결합될 수 있습니다. **LLM은 이런 서비스 전체가 아니라, 입력 맥락을 바탕으로 출력을 생성하는 모델을 뜻합니다.**


## AI 에이전트의 핵심 구조: 감지·판단·행동

WEF의 2024년 보고서는 AI 에이전트를 환경을 감지하고, 목표를 위해 환경에 행동하는 시스템으로 설명합니다. 아래 도식은 보고서의 감지·판단·행동 구조를 참고해 이 글의 주제에 맞춰 새로 그렸습니다. 센서(sensors)는 환경에서 지각(percepts)을 받고, 제어센터(control centre)는 모델·계획·메모리와 도구 호출을 조정하며, 이펙터(effectors)는 행동(actions)을 환경에 전달합니다. 환경에는 디지털·물리적 기반시설이 모두 포함될 수 있습니다.

![AI 에이전트의 감지·판단·행동 구조를 보여주는 새 도식. 사용자 목표가 환경에 들어가고, 센서가 관측 정보를 제어센터로 전달합니다. 제어센터는 모델·계획·메모리와 도구 호출을 조정하며, 이펙터는 도구·API·기기를 실행해 환경을 바꾸고 실행 결과를 제어센터로 돌려줍니다.](/posts/ai-agent-harness/agent-core.svg)

*개념 참고: [World Economic Forum, Navigating the AI Frontier (2024)](https://www.weforum.org/publications/navigating-the-ai-frontier-a-primer-on-the-evolution-and-impact-of-ai-agents/), p. 7, Figure 1. 도식은 보고서가 설명하는 구성 요소를 바탕으로 이 글의 테마에 맞춰 새로 그렸습니다.*

코딩 에이전트에 대응해 보면 이 구성이 더 구체적으로 보입니다.

| 에이전트 구조 | 코딩 에이전트에서 볼 수 있는 예 |
| --- | --- |
| 센서 | 사용자 요청, 저장소 파일, 명령 실행 결과 |
| 제어센터 | LLM의 다음 행동 판단과 하네스의 맥락·상태·도구 호출 조정 |
| 이펙터 | 파일 읽기·수정, 터미널, 검색, API 호출 도구 |
| 환경 | 코드 저장소, 터미널, 연결된 서비스 |

제어센터를 LLM 하나와 같은 말로 보면 안 됩니다. WEF의 고급 에이전트 설명은 제어센터 안에 모델뿐 아니라 의사결정·계획, 메모리 관리, 도구가 함께 놓일 수 있다고 설명합니다. 코딩 에이전트에서는 LLM이 다음 도구 호출을 제안하고, 하네스가 그 호출을 맥락과 권한에 맞게 연결하며, 실행기가 실제 작업을 수행하는 식으로 역할을 나누어 볼 수 있습니다. 이 대응은 개념을 설명하기 위한 것이며, WEF 도식이 특정 코딩 제품의 내부 구현을 나타내는 것은 아닙니다.

이 그림이 에이전트의 바깥 구조를 보여준다면, 다음 그림은 코딩 에이전트에서 특히 헷갈리기 쉬운 **도구 호출과 명령 실행 사이**를 펼쳐 보여줍니다.

## 켄자쿠로 보는 LLM·에이전트·하네스

《주술회전》의 켄자쿠라는 캐릭터를 통해 LLM과 에이전트, 하네스의 관계를 이해합니다.

![《주술회전》의 켄자쿠 캐릭터를 통해 LLM, 하네스, 에이전트의 관계를 설명하는 개념도. 뇌만 있는 상태는 LLM, 몸은 하네스와 실행 환경, 목표에 따라 도구를 사용하는 전체 시스템은 에이전트를 나타냅니다.](/posts/ai-agent-harness/kenjaku-analogy.svg)

비유에서 **뇌만 있는 켄자쿠는 LLM**, 그 뇌가 다른 사람의 몸에 이식되어 몸이 가진 기능을 사용할 수 있는 상태는 **에이전트**에 해당합니다. 여기서 몸은 도구와 권한, 작업 상태를 연결하는 **하네스**를 가리킵니다. LLM이 목표에 따라 도구를 선택하고, 실행 결과를 받아 다음 단계를 정하는 전체 시스템이 에이전트입니다.

실제 시스템에서는 하네스와 명령을 실행하는 작업 환경이 분리될 수 있습니다. 하네스는 모델 호출, 대화 기록, 도구 선택과 결과 전달, 승인, 종료 조건을 관리하는 **운영 코드**입니다. [OpenAI의 에이전트 구조 문서](https://developers.openai.com/api/docs/guides/agents-api/architecture)도 하네스와 실행 환경을 구분합니다.

## LLM이 도구를 요청하고, 실행기가 명령을 수행합니다

코딩 에이전트가 터미널을 쓰는 장면은 LLM이 컴퓨터에 직접 접속해 명령을 실행하는 것으로 보이기 쉽습니다. 실제 흐름에서는 먼저 하네스가 모델 요청에 사용할 수 있는 도구의 이름, 설명, 입력 형식을 함께 제공합니다. 모델은 주어진 도구 가운데 다음 행동에 필요한 것을 고르고, 도구 이름과 인자를 담은 구조화된 호출을 반환합니다.

![하네스가 도구 명세를 모델에 제공하고, LLM이 구조화된 도구 호출을 반환합니다. 하네스가 형식과 권한을 확인해 실행기에 전달하고, 실제 결과를 다시 모델에 돌려줍니다.](/posts/ai-agent-harness/agent-loop.svg)

예를 들어 단순화한 호출은 다음과 같습니다.

```json
{"name":"run_command","arguments":{"command":"npm test"}}
```

여기서 **run_command**는 하네스가 모델에 제공한 도구의 이름이고, **npm test**는 그 도구에 넘기는 명령 인자입니다. 이 출력 자체가 터미널에서 실행된 것은 아닙니다. OpenAI API에서는 function call, Anthropic API에서는 tool_use 같은 항목으로 표현될 수 있으며, 실제 데이터 형식은 API마다 다릅니다. [OpenAI의 function calling 안내](https://developers.openai.com/api/docs/guides/function-calling/)는 모델이 호출을 반환한 뒤 애플리케이션 코드가 실행하고 결과를 돌려주는 절차를 설명합니다. [Anthropic의 tool use 안내](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)는 애플리케이션이 실행하는 클라이언트 도구와 제공자 인프라에서 실행하는 서버 도구를 구분합니다.

하네스는 호출의 도구 이름과 인자 형식을 확인하고, 설계된 권한·작업 범위·승인 정책을 적용한 뒤 등록된 도구 구현으로 전달합니다. run_command 도구라면 그 구현이 작업 환경에서 실제 셸 프로세스를 시작하고, 표준 출력(stdout), 오류 출력(stderr), 종료 코드를 수집합니다. 파일 수정이나 검색 도구라면 각각의 도구 구현이 파일이나 검색 서비스에 접근합니다. 즉, **LLM은 실행할 도구와 인자를 제안하고, 하네스와 실행 환경이 정책에 따라 실제 동작을 수행합니다.**

작업 결과는 해당 도구 호출과 연결된 응답으로 하네스에 돌아옵니다. 하네스가 그 결과를 다음 모델 입력에 포함하면, 모델은 오류를 분석해 다시 도구를 호출하거나 최종 답변을 작성합니다. 권한이 없거나 승인이 필요한 작업은 실행 전에 거절하거나 사람의 확인을 기다리도록 구성할 수 있습니다. 그래서 **도구 호출 요청이 있다는 사실만으로 실제 실행까지 허용됐다고 볼 수는 없습니다.**

사람이 매번 다음 단계를 직접 지정한다면 도구를 쓰는 챗 인터페이스에 가깝습니다. 목표를 주었을 때 모델이 상황에 따라 경로와 도구를 고르고, 실행 결과를 반영해 다음 단계를 정하도록 구성하면 에이전트 시스템으로 볼 수 있습니다. 언제 멈추고 언제 사람에게 물을지는 설정에 달려 있으므로, 에이전트라고 해서 무제한으로 혼자 일한다는 뜻은 아닙니다. [Anthropic은](https://www.anthropic.com/engineering/building-effective-agents) 미리 정해진 순서로 LLM과 도구를 실행하는 *워크플로*와, 모델이 경로와 도구 사용을 동적으로 결정하는 *에이전트*를 구분합니다.

## ‘에이전트’와 ‘하네스’는 어떻게 구분할까요?

용어가 미묘한 이유가 있습니다. 에이전트는 **일을 하는 시스템 전체**를, 하네스는 그 안에서 모델을 반복 호출하고 도구·상태·권한을 연결하는 **운영 구조**를 가리킬 때가 많습니다. 제품에 따라 하네스 안에 어디까지 포함시키는지 다르기 때문에 경계선을 하나로 고정하기 어렵습니다.

| 구분 | 핵심 역할 | 버그 수정 예시 |
| --- | --- | --- |
| LLM | 주어진 맥락에서 다음 출력과 도구 요청을 만드는 모델 | “테스트를 실행하자”를 선택합니다 |
| 하네스 | 맥락 구성, 모델 호출, 도구 라우팅, 승인·피드백·종료를 맡는 구조 | 테스트 요청을 검사하고 결과를 되돌려줍니다 |
| 실행 환경 | 파일과 명령이 실제로 작동하는 공간 | 저장소 파일, 터미널, 샌드박스 |
| 에이전트 | 목표를 받고 위 요소를 통해 작업을 이어 가는 전체 시스템 | 읽기 → 수정 → 테스트 → 보고 |

**따라서 “모델 + 루프 = 에이전트”는 시작하기 좋은 축약이지만, 실무에서는 도구와 권한, 작업 환경, 종료·승인 조건까지 보아야 합니다.** 하네스를 ‘모델을 뺀 나머지 전부’로 설명하는 경우도 있지만, 실제 설계에서는 실행 환경을 별도로 떼어 놓는 편이 더 정확할 때가 있습니다. 반대로 제품 이름 자체가 에이전트인 동시에 하네스 구현을 가리키기도 합니다. 단어의 소속을 따지는 것보다 “누가 결정하고, 누가 실행하며, 누가 허용하는가”를 묻는 편이 도움이 됩니다.

이 차이는 같은 모델을 놓고 비교할 때 특히 잘 드러납니다. 한쪽은 저장소를 읽을 수만 있고, 다른 쪽은 테스트를 실행하고 변경 사항을 검사할 수 있다면 작업 경로가 다릅니다. **결과의 차이를 전부 하네스 덕분이라고 단정할 수는 없습니다.** 모델 성능, 과제, 도구 설명, 데이터, 권한, 사람의 개입도 함께 통제해야 원인을 비교할 수 있습니다. [Anthropic의 도구 설계 논의](https://www.anthropic.com/engineering/building-effective-agents/)가 도구의 설명과 사용성에 신경 쓰는 이유도 여기에 있습니다.

## 자율성과 권한: 에이전트에 맡기는 범위

도구가 많으면 좋은 에이전트일까요? 항상 그렇지는 않습니다. 모델이 **스스로 다음 단계를 고를 수 있는 정도**와, **외부 세계에 어느 범위까지 손을 뻗을 수 있는지**는 다른 축입니다.

| 상황 | 자율성 | 실행 권한 | 사람의 확인이 필요한 지점 |
| --- | --- | --- | --- |
| 파일을 읽고 요약하는 도우미 | 여러 문서를 스스로 찾아볼 수 있습니다 | 읽기만 허용 | 인용과 해석이 맞는지 확인합니다 |
| 코드를 고치고 테스트하는 도우미 | 오류에 따라 수정 경로를 바꿉니다 | 특정 저장소의 수정·테스트 허용 | 커밋·배포 전에 변경 내용을 검토합니다 |
| 고객에게 답장을 보내는 도우미 | 초안과 근거를 스스로 구성합니다 | 발송 권한은 보류할 수 있습니다 | 외부 발송 직전 승인 |

아래 상황들은 자율성과 실행 권한을 나누어 보여주는 **설계 예시**이며, 특정 제품의 기본 설정을 뜻하지 않습니다. WEF의 2025년 보고서는 에이전트를 기능, 역할, 예측 가능성, 자율성, 권한이라는 다섯 특성과 쓰임새, 운영 환경이라는 두 맥락 축으로 살펴봅니다. 이 분류를 출발점으로 평가, 위험 평가, 거버넌스를 연결하는 프레임워크를 제안합니다. [WEF 보고서 PDF 원문을 열거나 내려받을 수 있습니다.](https://reports.weforum.org/docs/WEF_AI_Agents_in_Action_Foundations_for_Evaluation_and_Governance_2025.pdf)

보고서가 제안하는 네 단계는 서로 다른 질문에 답합니다. **분류**는 에이전트가 무엇을 어떤 환경에서 하는지 정리하고, **평가**는 그 조건에서 성능과 한계를 확인합니다. 평가 항목으로는 과제 성공률과 완료 시간, 도구 호출 성공률, 예외 상황에서의 견고성, 오류 유형, 신뢰 지표 등이 제시됩니다. **위험 평가**는 이런 근거를 사용해 실패나 오용의 가능성과 피해 정도를 분석합니다. 마지막 **거버넌스**는 그 결과에 맞춰 접근 통제, 사람의 감독, 기록·모니터링 같은 보호 조치를 정합니다. 즉, 모델 답변의 정확도만 재는 대신 실제 과제에서 에이전트가 도구를 어떻게 쓰는지까지 평가 범위에 포함합니다.

실무에서는 “테스트를 실행해도 되는가”, “외부로 전송할 수 있는가”, “삭제는 승인 후에만 가능한가” 같은 질문이 기능 소개와 함께 검토돼야 합니다. 같은 터미널 도구도 권한 범위에 따라 실행 가능한 행동이 달라집니다. [OpenAI의 샌드박스 설명](https://developers.openai.com/api/docs/guides/agents/sandboxes/)처럼 하네스의 승인·기록과 실제 실행 공간의 파일·자격증명을 분리할 수도 있습니다.

## 실제로 어떤 에이전트들이 있나

에이전트 제품은 연결하는 작업 환경과 도구에 따라 역할이 달라집니다. 아래 표는 2026년 9월 23일에 확인한 공식 자료를 바탕으로 각 프로젝트의 주요 사용 환경과 기능을 요약합니다. 동일 조건에서 제품 성능을 비교한 결과는 아닙니다.

| 제품 | 주요 사용 맥락 | 공식 자료 |
| --- | --- | --- |
| Claude Code | 코드 저장소를 읽고 수정하며 명령을 실행하는 코딩 에이전트. 터미널·IDE·데스크톱·웹에서 제공 | [Claude Code 개요](https://code.claude.com/docs/en/overview) |
| Codex | 파일을 읽고 고치고 실행하는 OpenAI의 코딩 에이전트. CLI에서는 로컬 저장소와 도구를 사용 | [Codex CLI](https://developers.openai.com/codex/cli) |
| OpenCode | 모델과 도구 접근 권한을 구성할 수 있는 오픈소스 코딩 에이전트. 작업용·계획용 에이전트를 나누어 설정 가능 | [OpenCode 에이전트](https://opencode.ai/docs/agents/) |
| Pi 코딩 에이전트 | 작은 기본 구성에서 시작해 확장과 스킬로 원하는 작업 방식을 만드는 터미널 하네스 | [Pi 문서](https://pi.dev/docs/latest) |
| Oh My Pi(omp) | Pi에서 갈라져 나온 코딩 에이전트. 언어 서버(LSP), 디버거, 추가 도구 등을 통합하는 방향 | [Oh My Pi 저장소](https://github.com/can1357/oh-my-pi) |
| Hermes Agent | Nous Research의 에이전트 프로젝트. 터미널 작업에 더해 세션 간 기억·스킬과 메시징 연결을 강조 | [Hermes Agent 문서](https://hermes-agent.nousresearch.com/docs/) |
| OpenClaw | 여러 메시지 앱을 에이전트의 세션·도구·자동화와 연결하는 자체 호스팅 게이트웨이 | [OpenClaw 문서](https://docs.openclaw.ai/) |

**Hermes Agent는 Hermes라는 언어 모델이 아니라 Nous Research의 에이전트 프로젝트입니다.** OpenClaw는 코드 편집기보다 메시지 채널, 세션, 도구, 자동화를 잇는 게이트웨이 역할에 무게가 있습니다. Pi와 Oh My Pi는 계보가 이어지지만 서로 다른 프로젝트입니다.

이 제품들을 쓰다 보면 **MCP**, **스킬**, **메모리**라는 말도 같이 만납니다. MCP는 에이전트나 모델의 이름이 아니라 앱이 외부 도구·자료와 연결되는 [프로토콜](https://modelcontextprotocol.io/specification/2025-11-25/architecture)입니다. 스킬은 특정 업무를 수행할 때 참고할 절차나 자료를 묶어 둔 것이며, 그것만 적는다고 새 실행 권한이 생기는 것은 아닙니다. [Pi의 스킬 문서](https://pi.dev/docs/latest/skills/)와 [확장 문서](https://pi.dev/docs/latest/extensions/)는 읽는 지침과 실제 실행 기능을 추가하는 코드를 구분합니다. 메모리는 세션 사이에 남기는 기록이며, KV Cache와 역할이 다릅니다. [Hermes Agent의 문서](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)에서 설명하는 지속 메모리가 이런 층에 가깝습니다.

코딩 에이전트는 파일 수정과 테스트를 이어 가고, 메시징 중심 에이전트는 채널에서 작업을 받아 [예약한 시간에 실행](https://docs.openclaw.ai/automation)할 수도 있습니다. 이때 작업이 시작되는 장소와 일정도 운영 구조의 일부가 됩니다. 사람이 지켜보지 않는 동안 실행된다면 권한 범위와 결과 기록을 구체적으로 정해야 합니다.

## 실제 과제에서는 어떻게 쓰일까

작은 과제 하나를 처음부터 끝까지 맡기면 모델의 도구 요청, 하네스의 승인, 실행 결과가 어떻게 오가는지 확인할 수 있습니다. 이 방식은 각 구성 요소의 역할을 구분하는 데 도움이 됩니다.

예를 들어 “이 저장소의 로그인 테스트가 왜 실패하는지 찾아 주시겠어요? 외부 전송이나 배포는 하지 말아 주세요”라고 맡깁니다. 에이전트가 관련 파일을 읽고 테스트를 실행하면 ‘요청한 도구’, ‘허용된 행동’, ‘테스트 결과’, ‘그 결과에 따라 선택한 다음 행동’을 순서대로 확인할 수 있습니다. 작업이 성공하더라도 변경 내용과 테스트 범위는 검토해야 합니다. 각 단계의 기록은 모델의 판단, 도구 지원, 작업 맥락 중 어디에서 문제가 생겼는지 살펴보는 단서가 됩니다.

문서 정리나 데이터 분석에도 같은 원리를 적용할 수 있습니다. 자료를 읽어 비교표를 만들고 근거 링크를 남기거나, 허용된 데이터 폴더에서 스크립트를 실행한 뒤 오류를 수정하는 방식입니다. 다만 외부 발송·결제·운영 배포처럼 되돌리기 어려운 행동에는 별도의 승인 경계를 두어야 합니다. [WEF의 평가 관점](https://www.weforum.org/stories/artificial-intelligence/ai-agents-onboarding-governance/)을 빌리면 모델의 정답률만 볼 게 아니라 실제 과제에서 도구를 제대로 쓰는지, 장시간 실행 중 행동이 어떻게 바뀌는지, 권한이 적절한지도 확인해야 합니다.

반면 질문 한 번으로 답을 얻거나 순서가 항상 같은 작업에는 에이전트 루프가 필요하지 않을 수 있습니다. 모델 한 번 호출이나 고정된 자동화가 더 단순하고 검증하기 쉽습니다. [Anthropic도](https://www.anthropic.com/engineering/building-effective-agents) 복잡한 에이전트는 시간과 비용을 더 쓰므로, 간단한 방식으로 해결할 수 있는지 먼저 살펴보라고 권합니다.

정리하면, AI 에이전트는 모델의 이름만으로 설명되지 않습니다. 맡은 목표, 연결된 도구와 실행 권한, 결과를 다음 판단에 반영하는 구조를 함께 살펴야 합니다.
