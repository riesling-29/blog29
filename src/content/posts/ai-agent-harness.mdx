## 먼저 요약

에이전트를 설명할 때 가장 자주 생략되는 부분이 '하네스(harness)'다. 같은 LLM을 쓰더라도 어떤 지시문을 주는지, 어떤 도구를 노출하는지, 컨텍스트를 어떻게 관리하고, 결과를 어떻게 검증하는지에 따라 에이전트의 성공률이 크게 달라진다.

이 글의 핵심 주장은 다음 세 가지다.

- 에이전트는 "스스로 일하는 LLM"이 아니라 **모델을 감싸는 루프(하네스)와 모델의 결합**이다.
- 하네스는 지시문, 도구 정의, 컨텍스트 관리, 실행 환경, 검증·피드백, 오케스트레이션으로 구성된다.
- 에이전트 제품을 평가할 때는 **모델 능력과 하네스 설계를 분리해서** 봐야 한다.

## AI 에이전트가 무엇인가

챗봇은 한 번의 질의에 하나의 응답을 반환한다. 반면 에이전트는 목표를 받아 여러 단계로 분해하고, 도구를 호출하여 외부 세계(파일 시스템, 터미널, API)와 상호작용한 뒤, 그 결과를 관찰해서 다음 행동을 결정하는 **루프**를 돌린다.

```text
목표 입력
  → (1) 모델이 현재 컨텍스트를 읽고 다음 행동을 선택
  → (2) 하네스가 도구 호출을 실행하고 결과를 기록
  → (3) 결과가 목표에 도달했는지 확인
  → 미달하면 (1)으로 복귀, 달성하면 종료
```

여기서 (1)만 LLM이고, (2)(3)과 루프 자체는 모델 바깥의 코드다. 이 글에서 '하네스'란 바로 그 모델 바깥의 구조 전체를 가리킨다. 엔진(모델)과 차assis(하네스)를 구분하지 않고 "이 AI가 잘한다"라고 말하는 것은, 자동차를 평가할 때 엔진만 보고 말하는 것과 같다.

## 하네스의 구성 요소

에이전트 하네스는 제품마다 이름은 다르지만, 대부분 다음 여섯 가지로 분해된다.

| 구성 요소 | 역할 | 실패하면 나타나는 증상 |
| --- | --- | --- |
| 지시문(시스템 프롬프트) | 목표·규칙·출력 형식 정의 | 범위를 벗어난 행동, 일관 없는 출력 |
| 도구 정의(function schema) | 모델이 호출할 수 있는 함수와 인자 스키마 | 잘못된 인자, 불필요한 탐색 반복 |
| 컨텍스트 관리 | 윈도우 내 정보의 선택·압축·요약 | 긴 작업에서 초기 지시가 잊히거나, 관련 없는 정보가 과부하됨 |
| 실행 환경과 권한 | 셸·파일·네트워크 접근과 샌드박스 | 위험한 조작, 재현 불가능한 결과 |
| 검증과 피드백 | 테스트·린터·자기 점검으로 오류를 회수 | 첫 시도 오류가 그대로 최종 결과가 됨 |
| 오케스트레이션 | 단일 루프 vs 서브에이전트 분업 | 복잡한 작업에서 컨텍스트 오염, 비용 폭증 |

각 구성 요소는 독립적으로 설계된다. 예를 들어 같은 모델이라도 도구를 "파일 읽기/쓰기/실행" 세 개로 묶느냐, 수십 개의 세부 함수로 나누느냐에 따라 모델의 선택 공간이 달라진다. 도구 하나당 스키마와 설명이 컨텍스트를 차지하므로, 도구 설계는 곧 **모델에게 무엇을 보여줄 것인가**의 문제다.

### 컨텍스트 관리가 하네스의 핵심인 이유

LLM은 한 번에 처리할 수 있는 토큰이 제한되어 있고, 긴 작업일수록 과거 지시와 중간 결과가 윈도우 밖으로 밀려난다. 그래서 실제 에이전트 하네스는 보통 다음 중 하나 이상을 조합한다.

- **압축(compaction)**: 대화 이력을 요약해서 컨텍스트를 줄인다.
- **외부 메모리**: 파일이나 데이터베이스에 상태를 기록하고 필요할 때 다시 불러온다.
- **서브에이전트**: 하위 작업을 별도 컨텍스트에서 돌리고, 결과만 상위 루프로 올린다.

이 세 기법은 모두 "모델이 매 단계 무엇을 보고 결정하는가"를 통제하기 위한 것이다. 모델의 능력은 고정된 상태에서, 하네스가 정보 흐름을 바꾸는 셈이다.

## 왜 하네스 차이가 결과를 바꾸는가

**확인된 사실:** Anthropic의 엔지니어링 문서와 OpenAI의 에이전트 관련 문서는 모두, 에이전트를 "도구를 가진 LLM 루프"로 정의하고 워크플로우(정해진 순서)와 에이전트(모델이 스스로 경로를 결정)를 구분한다. 또한 같은 기반 모델을 전제로 도구 설계·지시문·검증 단계가 성공률에 영향을 준다는 사례를 제시한다.

**판단:** 실무에서 "A 제품이 B 제품보다 잘한다"는 평가의 상당 부분은 모델 차이가 아니라 하네스 차이에서 온다. 근거는 다음 세 가지다.

1. **관측 가능한 변수가 다르다.** 같은 모델 API를 쓰는 두 에이전트 제품은 지시문, 도구 스키마, 컨텍스트 정책이 전부 다를 수 있다.
2. **오류 회수 경로가 다르다.** 검증 루프가 있는 하네스는 실패한 단계를 되돌아 수정하지만, 없는 하네스는 첫 오류를 최종 결과로 남긴다.
3. **비용 구조가 다르다.** 컨텍스트 압축과 서브에이전트 분업은 같은 작업의 토큰 소비를 크게 줄이거나 늘린다.

따라서 "어떤 모델이 좋은가"와 "어떤 하네스가 좋은가"는 별개의 질문이며, 제품 비교 시 둘을 섞어서 평가하면 어느 쪽이 원인인지 분리할 수 없다.

## 에이전트 시스템을 평가하는 방법

에이전트를 도입하거나 제품을 비교할 때 다음 순서로 보면 판단의 근거를 남길 수 있다.

1. **과업을 정의한다.** "코드를 잘 쓴다"가 아니라, 어떤 입력에서 어떤 산출물로, 어떤 검증 기준을 통과해야 하는지 정한다.
2. **하네스 구성을 문서화한다.** 지시문, 도구 목록, 컨텍스트 정책, 권한 범위, 검증 단계를 기록한다. 이 중 어느 것이 모델에 의존하지 않는 구조인지 구분한다.
3. **동일 과업으로 A/B 비교한다.** 가능하면 같은 모델을 다른 하네스에 넣고, 같은 하네스에 다른 모델을 넣어 두 축의 기여를 분리한다.
4. **실패 사례를 분류한다.** 실패가 "모델이 모르는 것"인지 "하네스가 정보를 못 전달한 것"인지에 따라 개선 대상이 다르다.

## 반증 조건과 유효기간

이 글의 사실 설명은 2026-08-16 기준으로, Anthropic·OpenAI 공식 문서와 주요 에이전트 제품의 공개 문서를 확인한 결과다. 다음 중 하나가 확인되면 판단을 수정해야 한다.

- 모델 자체의 컨텍스트 처리 능력(예: 윈도우 크기, 장기 기억)이 하네스 설계보다 성공률에 더 큰 영향을 준다는 재현 가능한 비교 결과가 나온다.
- "하네스"를 구성 요소로 분해하는 관행이 업계에서 폐기되고 단일 표준 추상화가 등장한다.
- 평가 대상 제품의 지시문·도구 스키마가 공개되지 않아 하네스 분석 자체가 불가능한 상태가 고착된다.
