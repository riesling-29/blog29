Attention과 KV Cache 같은 LLM의 기본적인 지식을 배웠다는 전제하에 이야기를 시작해보겠습니다. Attention, KV Cache를 배우고 나면 이런 질문이 생기게 됩니다.
"LLM은 입력을 받아 다음 토큰을 만들어 내는 기능만 있는데, 어떻게 코드를 고치고 테스트까지 돌릴 수 있을까요? 모델 안에 터미널이 들어 있는 걸까요?"

답은 모델 *바깥*에 있습니다. 모델은 다음에 무엇을 할지 고르고, 별도의 프로그램이 그 요청을 받아 실행합니다. 실행 결과를 다시 모델에 보여 주면 모델은 다음 행동을 고릅니다. 이 왕복으로 동작하는 시스템을 AI 에이전트라고 부릅니다. 다만 어디까지를 에이전트라고 부를지는 자료마다 조금씩 다릅니다. [WEF가 소개한 전문가들의 설명](https://www.weforum.org/stories/technological-innovation/what-is-an-ai-agent-experts-explain/)에서도 자율성, 판단, 행동의 강조점이 서로 다릅니다.

## Attention에서 에이전트로

LLM은 입력된 토큰을 바탕으로 다음 출력을 만듭니다. Attention은 지금 처리하는 토큰이 앞선 맥락의 어느 부분을 참고할지 계산하는 데 쓰입니다. KV Cache는 이미 처리한 토큰의 key와 value를 생성 과정에서 재활용해 매번 다시 계산하는 일을 줄입니다. 여기까지는 **모델이 주어진 맥락을 처리하는 방식**에 관한 이야기입니다. [Hugging Face의 캐시 설명](https://huggingface.co/docs/transformers/main/cache_explanation/)을 떠올리면 됩니다.

하지만 KV Cache가 파일을 열거나, 어제의 작업을 영구히 기억하거나, 테스트 결과를 알아서 가져오는 것은 아닙니다. 대화 이력과 파일, 도구 결과 중 무엇을 다음 호출에 넣을지는 모델 바깥의 시스템이 관리합니다. 서비스에 따라 맥락을 다시 구성할 수도 있고 일부 계산을 재활용할 수도 있습니다. **KV Cache와 에이전트의 작업 기억을 같은 것으로 놓으면 여기서부터 헷갈립니다.**

여기서 한 가지 단서를 구분해야 합니다. 요즘 AI 서비스는 텍스트만 다루지 않고 이미지나 음성, 검색·코드 실행 도구를 포함하기도 합니다. 아래의 ‘LLM’은 설명을 위해 **모델 자체의 판단 부분**을 가리키며, ChatGPT나 Claude 같은 서비스 전체와 동일한 말은 아닙니다.

## 켄자쿠의 뇌와 몸으로 보는 LLM·하네스

《주술회전》의 켄자쿠는 뇌만 있는 상태와 다른 사람의 몸에 이식된 상태를 구분해 볼 수 있는 인물입니다. 여기서는 이 설정을 LLM, 에이전트, 하네스의 관계를 설명하는 **예시로만** 사용합니다.

![켄자쿠 이미지를 포함한 개념도. 뇌와 몸이 함께 있는 켄자쿠 이미지를 전체 비유의 중심에 두고, 아래 화살표는 LLM의 판단, 하네스와 실행 환경, 에이전트 시스템의 관계를 보여 줍니다.](/posts/ai-agent-harness/kenjaku-analogy.svg)

비유에서 **뇌만 있는 켄자쿠는 LLM**, 그 뇌가 다른 사람의 몸에 이식되어 몸이 가진 기능을 사용할 수 있는 상태는 **에이전트**에 해당합니다. 여기서 몸은 도구와 권한, 작업 상태를 연결하는 **하네스**를 가리킵니다. LLM이 목표에 따라 도구를 선택하고, 실행 결과를 받아 다음 단계를 정하는 전체 시스템이 에이전트입니다.

이 대응은 개념을 구분하기 위한 짧은 비유입니다. 실제 하네스는 모델 호출, 대화 기록, 도구 선택과 결과 전달, 승인, 종료 조건을 다루는 **운영 코드**이며, 명령을 실행하는 **작업 환경**과 분리될 수 있습니다. [OpenAI의 에이전트 구조 문서](https://developers.openai.com/api/docs/guides/agents-api/architecture)도 하네스와 실행 환경을 구분합니다.

## 모델의 ‘도구를 쓰겠다’와 실제 실행 사이

“이 코드의 버그를 찾아서 고쳐 주세요”라는 요청을 넣었다고 가정해 보겠습니다. 모델이 처음부터 정답을 알 필요는 없습니다. 파일을 읽고, 의심되는 부분을 찾고, 테스트를 실행한 다음, 나온 오류에 따라 다음 행동을 바꿀 수 있습니다.

![에이전트의 작업 흐름. 목표와 맥락을 모델에 전달하고 도구 요청을 확인한 뒤 실행 결과를 다시 모델에 돌려주는 루프.](/posts/ai-agent-harness/agent-loop.svg)

예컨대 모델이 다음과 같은 **요청**을 출력할 수 있습니다. 이 코드는 특정 제품의 실제 API 형식이 아니라 설명용입니다.

```json
{"tool": "run_tests", "arguments": {"target": "auth"}}
```

요청을 받은 하네스는 `run_tests`라는 도구가 있는지, 지금 실행해도 되는지 확인합니다. 허용되면 테스트를 실행하고 결과를 모델에 다시 전달합니다. 실패하면 오류를 읽고 코드를 수정할지, 다른 파일을 더 볼지 고릅니다. [OpenAI의 function calling 문서](https://developers.openai.com/api/docs/guides/function-calling/)도 도구 제시 → 모델의 호출 요청 → 외부 실행 → 결과 반환 → 다음 응답이라는 왕복을 설명합니다.

반대로 권한이 없는 파일을 읽으려 했다면 하네스가 거절할 수 있습니다. 모델에는 “권한 없음”이라는 결과가 돌아가고, 그다음에는 허용된 방법을 찾거나 사람에게 승인을 요청해야 합니다. **도구를 호출할 수 있다는 것과 그 행동을 실제로 허용받았다는 점은 다릅니다.**

사람이 매번 다음 단계를 직접 지정한다면 도구를 쓰는 챗 인터페이스가 될 수 있습니다. 목표를 주었을 때 모델이 상황에 따라 경로와 도구를 고르고, 결과를 보고 다음 단계를 정하도록 구성하면 여기서 말하는 에이전트에 가깝습니다. 언제 멈출지와 언제 사람에게 물을지는 설정에 달려 있습니다. 에이전트라고 해서 무조건 무제한으로 혼자 일하는 것은 아닙니다. [Anthropic은](https://www.anthropic.com/engineering/building-effective-agents) 미리 정해진 순서로 LLM과 도구를 실행하는 *워크플로*와, 모델이 경로와 도구 사용을 동적으로 결정하는 *에이전트*를 구분합니다.

## ‘에이전트’와 ‘하네스’는 어떻게 구분할까요?

용어가 미묘한 이유가 있습니다. 에이전트는 **일을 하는 시스템 전체**를, 하네스는 그 안에서 모델을 반복 호출하고 도구·상태·권한을 연결하는 **운영 구조**를 가리킬 때가 많습니다. 제품에 따라 하네스 안에 어디까지 포함시키는지 다르기 때문에 경계선을 하나로 고정하기 어렵습니다.

| 구분 | 이 글에서의 의미 | 버그 수정 예시 |
| --- | --- | --- |
| LLM | 주어진 맥락에서 다음 출력과 도구 요청을 만드는 모델 | “테스트를 실행하자”를 선택합니다 |
| 하네스 | 맥락 구성, 모델 호출, 도구 라우팅, 승인·피드백·종료를 맡는 구조 | 테스트 요청을 검사하고 결과를 되돌려줍니다 |
| 실행 환경 | 파일과 명령이 실제로 작동하는 공간 | 저장소 파일, 터미널, 샌드박스 |
| 에이전트 | 목표를 받고 위 요소를 통해 작업을 이어 가는 전체 시스템 | 읽기 → 수정 → 테스트 → 보고 |

**따라서 “모델 + 루프 = 에이전트”는 시작하기 좋은 축약이지만, 실무에서는 도구와 권한, 작업 환경, 종료·승인 조건까지 보아야 합니다.** 하네스를 ‘모델을 뺀 나머지 전부’로 설명하는 경우도 있지만, 실제 설계에서는 실행 환경을 별도로 떼어 놓는 편이 더 정확할 때가 있습니다. 반대로 제품 이름 자체가 에이전트인 동시에 하네스 구현을 가리키기도 합니다. 단어의 소속을 따지는 것보다 “누가 결정하고, 누가 실행하며, 누가 허용하는가”를 묻는 편이 도움이 됩니다.

이 차이는 같은 모델을 놓고 비교할 때 특히 잘 드러납니다. 한쪽은 저장소를 읽을 수만 있고, 다른 쪽은 테스트를 실행하고 변경 사항을 검사할 수 있다면 작업 경로가 다릅니다. **결과의 차이를 전부 하네스 덕분이라고 단정할 수는 없습니다.** 모델 성능, 과제, 도구 설명, 데이터, 권한, 사람의 개입도 함께 통제해야 원인을 비교할 수 있습니다. [Anthropic의 도구 설계 논의](https://www.anthropic.com/engineering/building-effective-agents/)가 도구의 설명과 사용성에 신경 쓰는 이유도 여기에 있습니다.

## 자율성과 권한: 에이전트에 맡기는 범위

도구가 많으면 좋은 에이전트일까요? 항상 그렇지는 않습니다. 모델이 **스스로 다음 단계를 고를 수 있는 정도**와, **외부 세계에 어느 범위까지 손을 뻗을 수 있는지**는 다른 축입니다.

| 상황 | 자율성 | 실행 권한 | 사람의 확인이 필요한 지점 |
| --- | --- | --- | --- |
| 파일을 읽고 요약하는 도우미 | 여러 문서를 스스로 찾아볼 수 있습니다 | 읽기만 허용 | 인용과 해석이 맞는지 확인합니다 |
| 코드를 고치고 테스트하는 도우미 | 오류에 따라 수정 경로를 바꿉니다 | 특정 저장소의 수정·테스트 허용 | 커밋·배포 전에 변경 내용을 검토합니다 |
| 고객에게 답장을 보내는 도우미 | 초안과 근거를 스스로 구성합니다 | 발송 권한은 보류할 수 있습니다 | 외부 발송 직전 승인 |

이 표는 **설명용 설계 예시**입니다. 어떤 제품의 기본 권한 설정을 뜻하지 않습니다. WEF의 2025년 보고서는 에이전트를 기능, 역할, 예측 가능성, 자율성, 권한이라는 다섯 특성과 쓰임새, 운영 환경이라는 두 맥락 축으로 살펴봅니다. 이 분류를 출발점으로 평가, 위험 평가, 거버넌스를 연결하는 프레임워크를 제안합니다. [WEF 보고서 PDF 원문을 열거나 내려받을 수 있습니다.](https://reports.weforum.org/docs/WEF_AI_Agents_in_Action_Foundations_for_Evaluation_and_Governance_2025.pdf)

보고서가 제안하는 네 단계는 서로 다른 질문에 답합니다. **분류**는 에이전트가 무엇을 어떤 환경에서 하는지 정리하고, **평가**는 그 조건에서 성능과 한계를 확인합니다. 평가 항목으로는 과제 성공률과 완료 시간, 도구 호출 성공률, 예외 상황에서의 견고성, 오류 유형, 신뢰 지표 등이 제시됩니다. **위험 평가**는 이런 근거를 사용해 실패나 오용의 가능성과 피해 정도를 분석합니다. 마지막 **거버넌스**는 그 결과에 맞춰 접근 통제, 사람의 감독, 기록·모니터링 같은 보호 조치를 정합니다. 즉, 모델 답변의 정확도만 재는 대신 실제 과제에서 에이전트가 도구를 어떻게 쓰는지까지 평가 범위에 포함합니다.

실무에서는 “테스트를 실행해도 되는가”, “외부로 전송할 수 있는가”, “삭제는 승인 후에만 가능한가” 같은 질문이 기능 소개와 함께 검토돼야 합니다. 같은 터미널 도구도 권한 범위에 따라 실행 가능한 행동이 달라집니다. [OpenAI의 샌드박스 설명](https://developers.openai.com/api/docs/guides/agents/sandboxes/)처럼 하네스의 승인·기록과 실제 실행 공간의 파일·자격증명을 분리할 수도 있습니다.

## 실제로 어떤 에이전트들이 있나

여기서 이름을 나열하는 목적은 성능 순위를 정하는 것이 아닙니다. 같은 모델을 쓰더라도 **어떤 작업장과 도구를 연결해 주는가**를 비교해 보면 하네스가 눈에 들어옵니다. 다음은 2026년 9월 23일에 확인한 각 프로젝트의 공식 소개를 바탕으로 한, 입문자를 위한 위치 설명입니다.

| 제품 | 처음 볼 때 이해할 위치 | 공식 자료 |
| --- | --- | --- |
| Claude Code | 코드 저장소를 읽고 수정하며 명령을 실행하는 코딩 에이전트. 터미널·IDE·데스크톱·웹에서 제공 | [Claude Code 개요](https://code.claude.com/docs/en/overview) |
| Codex | 파일을 읽고 고치고 실행하는 OpenAI의 코딩 에이전트. CLI에서는 로컬 저장소와 도구를 사용 | [Codex CLI](https://developers.openai.com/codex/cli) |
| OpenCode | 모델과 도구 접근 권한을 구성할 수 있는 오픈소스 코딩 에이전트. 작업용·계획용 에이전트를 나누어 설정 가능 | [OpenCode 에이전트](https://opencode.ai/docs/agents/) |
| Pi 코딩 에이전트 | 작은 기본 구성에서 시작해 확장과 스킬로 원하는 작업 방식을 만드는 터미널 하네스 | [Pi 문서](https://pi.dev/docs/latest) |
| Oh My Pi(omp) | Pi에서 갈라져 나온 코딩 에이전트. 언어 서버(LSP), 디버거, 추가 도구 등을 통합하는 방향 | [Oh My Pi 저장소](https://github.com/can1357/oh-my-pi) |
| Hermes Agent | Nous Research의 에이전트 프로젝트. 터미널 작업에 더해 세션 간 기억·스킬과 메시징 연결을 강조 | [Hermes Agent 문서](https://hermes-agent.nousresearch.com/docs/) |
| OpenClaw | 여러 메시지 앱을 에이전트의 세션·도구·자동화와 연결하는 자체 호스팅 게이트웨이 | [OpenClaw 문서](https://docs.openclaw.ai/) |

여기서 **Hermes Agent는 ‘Hermes’라는 모델 자체와 구분**해서 읽는 것이 좋습니다. 또한 OpenClaw는 코드 편집 화면 하나라기보다 메시지 채널, 세션, 도구, 자동화를 이어 주는 운영 층에 무게가 있습니다. Pi와 Oh My Pi는 계보가 이어지지만 동일 제품은 아닙니다. 이 구분은 공식 소개를 보고 이해하기 위한 것이며, 작업 성공률이나 안전성을 독립적으로 시험해 매긴 평가가 아닙니다.

이 제품들을 쓰다 보면 **MCP**, **스킬**, **메모리**라는 말도 같이 만납니다. MCP는 에이전트나 모델의 이름이 아니라 앱이 외부 도구·자료와 연결되는 [프로토콜](https://modelcontextprotocol.io/specification/2025-11-25/architecture)입니다. 스킬은 특정 업무를 수행할 때 참고할 절차나 자료를 묶어 둔 것이며, 그것만 적는다고 새 실행 권한이 생기는 것은 아닙니다. [Pi의 스킬 문서](https://pi.dev/docs/latest/skills/)와 [확장 문서](https://pi.dev/docs/latest/extensions/)는 읽는 지침과 실제 실행 기능을 추가하는 코드를 구분합니다. 메모리는 세션 사이에 남기는 기록이며, KV Cache와 역할이 다릅니다. [Hermes Agent의 문서](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)에서 설명하는 지속 메모리가 이런 층에 가깝습니다.

사용 방식도 넓어졌습니다. 코딩 도구에서는 파일 수정과 테스트를 이어 가고, 메시징 중심 도구에서는 채널을 통해 작업을 받고 [예약한 시간에 다시 실행](https://docs.openclaw.ai/automation)할 수도 있습니다. 이것은 한 제품이 모든 일을 알아서 안전하게 한다는 뜻이 아니라, **작업을 시작하는 장소와 주기까지 하네스의 일부가 되었다**는 관찰입니다. 사람이 없을 때 실행하는 작업일수록 권한 범위와 결과 기록을 더 구체적으로 정해야 합니다.

## 실제 과제에서는 어떻게 쓰일까

입문 단계에서는 ‘완전 자율’ 시연보다 **작은 과제에서 모델의 요청과 실행 결과가 어떻게 왕복하는지 확인하는 방식**이 구조를 이해하는 데 적합합니다.

예를 들어 “이 저장소의 로그인 테스트가 왜 실패하는지 찾아 주시겠어요? 외부 전송이나 배포는 하지 말아 주세요”라고 맡깁니다. 에이전트가 관련 파일을 읽고 테스트를 실행하면, 참가자는 ‘요청한 도구’, ‘실제로 허용된 행동’, ‘테스트 결과’, ‘그 결과를 보고 고른 다음 행동’을 순서대로 볼 수 있습니다. 성공하더라도 사람이 diff와 테스트 범위를 검토해야 합니다. 이 과정에서 모델이 뛰어난지, 도구가 부족한지, 맥락이 빠졌는지를 구별할 단서가 생깁니다.

문서 정리나 데이터 분석에도 같은 원리를 적용할 수 있습니다. 자료를 읽어 비교표를 만들고 근거 링크를 남기거나, 허용된 데이터 폴더에서 스크립트를 실행한 뒤 오류를 수정하는 방식입니다. 다만 외부 발송·결제·운영 배포처럼 되돌리기 어려운 행동에는 별도의 승인 경계를 두어야 합니다. [WEF의 평가 관점](https://www.weforum.org/stories/artificial-intelligence/ai-agents-onboarding-governance/)을 빌리면 모델의 정답률만 볼 게 아니라 실제 과제에서 도구를 제대로 쓰는지, 장시간 실행 중 행동이 어떻게 바뀌는지, 권한이 적절한지도 확인해야 합니다.

반면 질문 한 번으로 답을 얻거나 순서가 항상 같은 작업이면 에이전트 루프가 필요하지 않을 수 있습니다. 모델 한 번 호출이나 고정된 자동화가 더 단순하고 검증하기 쉽습니다. [Anthropic 역시](https://www.anthropic.com/engineering/building-effective-agents) 복잡한 에이전트가 시간과 비용을 더 쓰는 만큼, 간단한 방식으로 해결되는지 먼저 살펴보라고 권합니다. 이 글의 사례들은 사용법을 설명하기 위한 것이며, 실제 제품을 동일 조건에서 비교한 실험 결과는 아닙니다.

정리하면, AI 에이전트는 모델의 이름만으로 설명되지 않습니다. 맡은 목표, 연결된 도구와 실행 권한, 결과를 다음 판단에 반영하는 구조를 함께 살펴야 합니다.

## 이 블로그 글은 이렇게 쓰였습니다

이번 글의 작성과 공개에는 두 가지 작업 경로가 사용되었습니다.

1. **Local LLM + Hermes**  
   로컬에서 실행하는 LLM을 Hermes를 통해 사용해 글의 초안을 만들고 내용을 정리합니다. 모델과 에이전트 실행 환경이 개인 컴퓨터 안에서 연결되는 흐름입니다.

2. **GPT/Codex + GitHub + Vercel**  
   Codex가 GitHub 저장소의 원고를 수정하고, Vercel이 변경 사항을 블로그로 배포합니다. 여기서 GPT는 글과 코드를 다루는 모델을, Codex는 GitHub 저장소를 읽고 수정하는 코딩 에이전트 환경을 가리킵니다.

### 처음 한 번 연결하기

**1. Codex에 GitHub 저장소 연결하기**

1. [Codex](https://chatgpt.com/codex)에 ChatGPT 계정으로 로그인한 뒤 GitHub 연결을 시작합니다.
2. GitHub로 이동하면 Codex 앱 설치와 권한 부여를 진행합니다. 저장소를 고르는 화면에서는 필요한 저장소만 선택하는 방식이 적절합니다. 조직 저장소라면 조직 관리자의 승인이 필요할 수 있습니다.
3. Codex로 돌아와 연결할 저장소를 선택하고 작업 환경을 만듭니다. 저장소에 별도 빌드나 검사 명령이 있다면 환경에 설정합니다.

일반 ChatGPT의 GitHub 연결 앱은 저장소 내용을 검색하고 분석하는 읽기 전용 연결입니다. 파일을 수정하거나 변경 사항을 GitHub에 올리는 작업은 Codex에서 진행합니다. 연결 가능한 기능은 ChatGPT 요금제와 화면에 따라 다를 수 있으므로 [GitHub 연결 안내](https://help.openai.com/en/articles/11145903-connecting-github-to-chatgpt)와 [Codex Cloud 빠른 시작](https://developers.openai.com/codex/cloud)을 함께 확인하면 됩니다.

**2. Vercel에 같은 GitHub 저장소 연결하기**

1. Vercel 대시보드에서 **New Project**를 선택하고 GitHub 저장소를 가져옵니다. 이미 Vercel 프로젝트가 있다면 **Project Settings → Git**에서 연결된 저장소를 확인합니다.
2. Vercel의 GitHub 앱이 저장소에 접근하도록 승인합니다. Codex와 Vercel은 별개의 앱이므로 각각 저장소 접근 권한을 받아야 합니다.
3. 프로젝트의 프레임워크와 Root Directory를 확인하고, 필요한 환경 변수와 빌드 설정을 지정한 뒤 첫 배포를 완료합니다.
4. **Production Branch**가 실제 공개 브랜치와 맞는지 확인합니다. 이 블로그에서는 `main`이 공개 브랜치입니다.

Vercel은 연결된 Git 저장소의 변경을 빌드합니다. 기본 설정에서는 일반 브랜치의 변경 사항에 미리보기 배포를 만들고, Production Branch에 반영된 변경 사항을 운영 사이트에 배포합니다. 브랜치 설정이나 빌드가 실패하면 배포가 완료되지 않을 수 있습니다. 자세한 설정은 [Vercel Git 배포 안내](https://vercel.com/docs/git)와 [GitHub 연동 문서](https://vercel.com/docs/git/vercel-for-github)를 참고할 수 있습니다.

### 글을 수정하고 공개하기

1. Codex에 저장소와 수정할 파일 경로, 원하는 변경 사항을 구체적으로 알려줍니다. 예를 들어 “`src/content/posts/ai-agent-harness.mdx`의 해당 절만 수정하고, 다른 파일은 바꾸지 말아 주세요”처럼 범위를 지정합니다.
2. Codex가 제안한 변경 요약과 diff를 확인합니다. 문장, 링크, 그림 경로와 함께 의도하지 않은 파일 변경이 없는지 살펴봅니다.
3. 공개 전에 확인하려면 별도 브랜치에서 작업한 뒤 Pull Request를 엽니다. Vercel이 만든 미리보기 주소에서 글과 그림을 확인하고, 문제가 없으면 Pull Request를 `main`에 병합합니다.
4. `main`에 반영되면 Vercel이 운영 배포를 시작합니다. Vercel 대시보드에서 상태가 성공인지 확인한 다음 실제 블로그 주소를 열어 최종 결과를 확인합니다.

수정 내용을 바로 `main`에 올리는 방식도 가능하지만, 그 경우 운영 배포가 곧바로 시작될 수 있습니다. 미리보기에서 먼저 확인하는 흐름은 공개 사이트에 반영하기 전에 결과를 검토할 시간을 줍니다.
